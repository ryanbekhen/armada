# CLAUDE.md

Guidance for Claude Code when working in this repository.

## About the project

Armada is a multi-machine container platform (cloud instances, VMs, or bare metal; do not describe it as VPS-specific). Docs describe Armada on its own terms: do not compare it with or name other products unless a component or protocol really needs naming. Two binaries, written in Rust (ADR 0027, ADR 0055): `armadad` runs on every machine as root, as `armadad server` (control plane) and `armadad agent` (runs containers on the supervisor runtime through the runtime pack's `armada-node`, ADR 0046, ADR 0054), plus the machine commands (`init`, `join`, `doctor`, `backup`, `restore`, `runtime`); `armada` is the client that only talks to the API (no root, Linux and macOS). Ingress uses HAProxy as a system container managed by Armada.

- **Architecture decisions:** `docs/adr/`. **Threat model:** `docs/threat-model.md`

When the design changes, add or update an ADR in the same change. Never let code and documents contradict each other (see "Keeping documents current" below).

## Status

Armada is about to go beta. A cluster has one control plane server or three (each machine runs `armada-etcd`, `armada-server`, and `armada-agent` as systemd units, ADR 0009, ADR 0010, ADR 0055) and any number of nodes (`armada-agent`), every node on the supervisor runtime (`armada-shim` with crun, ADR 0046, ADR 0056) with HAProxy as its proxy and `armada-dns` as its resolver. Done and supported: apps with rolling updates, rollbacks, restarts, probes, self-healing, placement, and rebalancing (ADR 0005, ADR 0008, ADR 0013, ADR 0014); jobs and cron (ADR 0019); autoscaling on CPU, memory, requests, queues, and schedules, scale to zero, and traffic splitting (ADR 0020, ADR 0021, ADR 0022, ADR 0034); init containers and sidecars (ADR 0038); internal HTTP and TCP ingress (ADR 0007, ADR 0039); persistent, backed-up, failing-over, and NFS volumes (ADR 0023, ADR 0041, ADR 0042); spaces with network isolation, users, services, and roles (ADR 0026, ADR 0033); space secrets and spec variables (ADR 0029, ADR 0052); exec, top, metrics, events, log history and export, and alerts (ADR 0015 to ADR 0018, ADR 0043 to ADR 0045); certificates through HTTP-01 and Cloudflare DNS-01, also with an app's own token (ADR 0047); the cluster network in the `plain`, `wireguard`, and `mesh` modes, switching modes, more than one site, and nodes behind NAT (ADR 0025, ADR 0049, ADR 0050); the client through an SSH host (ADR 0048); release checks and verified upgrades (ADR 0030); control plane backups to a bucket and restores (ADR 0051); `armadad doctor`; the signed release pipeline (GoReleaser + cosign + SBOM + provenance) and `install.sh`. Tested end to end (`docs/tested-environments.md`): local lab VMs with Pebble ACME, a single server on Oracle Cloud (arm64, Oracle Linux 9, SELinux enforcing, Let's Encrypt staging, HTTP-01 and Cloudflare DNS-01 wildcard), three control plane servers on depa.id under load (leader stop and SIGKILL, rolling updates through the new leader, all machines rebooted at once), a mixed amd64/arm64 cluster, and the `wireguard` mode with the kernel device. Upgrades into this release come only from v0.1.0-alpha.44 (`test/e2e/upgrade.sh`); downgrades are refused. A node still on containerd (`agent.json` `"runtime": "embedded"` or none) runs nothing here: its agent starts nothing and doctor fails, both saying to upgrade through v0.1.0-alpha.44 first. The conformance suite on crun has not run on a lab node yet. Do not build features outside the agreed scope unless asked.

Toolchain: Rust, pinned in `rust-toolchain.toml` at the root and in `logger/`, `shim/`, and `dns/` (with rustfmt, clippy, and both musl targets); every crate pinned in `Cargo.lock`, every build `--locked`; `[profile.dev]` keeps line tables only.

```bash
armada cluster update --mesh-cidr CIDR / armadad join|server join --no-private-ip   # range of mesh addresses for machines of another site with no private network (default 10.122.0.0/16, before the first joins) / join from another site with a mesh address (ADR 0050)
armada space create|list|show|use|delete NAME  # spaces (ADR 0026); use saves it in the client config; --space P (or ARMADA_SPACE) or NAME.SPACE override; -A lists every space
armada space update default --network-isolation[=false]   # isolate the default space's containers from the platform (others always are)
armada user create NAME -o FILE [--role ROLE [--space P]] [--ssh [USER@]HOST] / user list|show|credentials|update|delete   # a user certificate per person (ADR 0033); --ssh writes a config that reaches the servers through `ssh -W` (ADR 0048)
armada service create|list|show|credentials|renew|update|delete; role list|show ROLE; role grant|revoke ROLE --user U|--service S [--space P]   # services and roles (ADR 0033); role list shows who holds each (cluster-admin)
```

## Architecture in brief

Where things live: `server/src` is the control plane (one file per area: `reconcile.rs` the pass, `schedule.rs` placement, `apps.rs`, `jobs.rs`, `triggers.rs`, `autoscale.rs`, `volumes.rs`, `backups.rs`, `failover.rs`, `cpbackup.rs`, `network.rs`, `ingress.rs`, `certs.rs` and `acme/`, `assign.rs` assignments, `agents.rs` sessions, `usage.rs`, `events.rs`, `alert.rs`/`alerts.rs`, `metrics.rs`, `logs.rs`, `exec.rs`, `access.rs`/`rbac.rs`/`guard.rs`/`grpc.rs`/`conn.rs`, `join.rs`, `lifecycle.rs` and `renew.rs`); `store/src` the keyspace in etcd and its client (`tx.rs`, `client.rs`, `election.rs`, `records.rs`, `migrate.rs`); `agent/src` the node agent (`agent.rs` the pass, `session.rs`, `proxy.rs`, `network.rs`, `wake.rs`, `runcleft.rs`; the sessions beside the pass in `agent/src/side`; the supervisor runtime in `agent/src/supervisor`; HAProxy's driver in `agent/src/haproxy`; `clusternet.rs`; `dnsprocess.rs`); `node/src` armada-node, the program and library the agent and daemon call for the runtime (`runtime/`: images, root filesystems, bundles, OCI specs, shims, exec), the cluster network (`net/`), the HAProxy renderer (`proxy/`), volumes (`volume/`, `volbackup/`), queues (`queue/`), NFS, and connection tracking; `client/src` the `armada` client (`cli/` the command framework, `commands/`, `config.rs`, `dial.rs`, `release.rs`); `daemon/src` `armadad` (`commands/`, `backup.rs`, `pack.rs`, `state.rs`, `machine.rs`); `spec/src` specs (YAML strictly, validation, export, variables, cron); `pki/src`, `secrets/src`, `fsutil/src`; `proto/` the protocol's generated code; `dns/` armada-dns, `logger/` armada-log, `shim/` armada-shim. Every binary is its own program: `armada` never links `armadad` or what a machine needs (`client/tests/dependencies.rs`), and neither picks its role from its name.

- **Desired state + reconciliation**: the CLI only writes desired state to the server; reconcilers on the server and agents converge actual state. Every operation goes through this path; never add a "just run the container" path from the CLI.
- Agents open the gRPC (mTLS) connection to the server; the server sends assignments over a bidirectional stream (`Connect`; `server/src/agents.rs`, `assign.rs`; the agent's side in `agent/src/session.rs`).
- Nodes (ADR 0003): joining goes through a separate join listener (server-only TLS, serves only `JoinService`, rate limited, connections bounded before TLS (256, 16 per source) and closed after 15 s idle or 2 min; `server/src/conn.rs`, `join.rs`); the main API is always strict mTLS. The joining node pins the CA by hash (`daemon/src/joinclient.rs`). Node certificates last 30 days, are renewed by the agent (`agent/src/creds.rs`), and are only accepted while their serial is recorded (removing a node revokes them; `RemoveNode` first queues an empty assignment on the node's session, flushed before the session ends, so the removed agent stops what it ran). Each server renews its own server and etcd member certificates (`server/src/renew.rs`: at start, then every 12h, `pki::renew_due` = last third or expired) with the same key; the API, join, and metrics listeners serve the current one on every handshake, and the etcd client reads the member files per handshake. At start the server re-signs the machine's expired node certificate for the agent unit (a removed node is refused). Doctor's `certificates` check warns and fails on expiry. Cordoned nodes get no new replicas and are evacuated without dropping below the desired serving count. Unevenly spread apps are rebalanced one replica at a time (ADR 0013). Placement (ADR 0014; `server/src/schedule.rs`): admin-only node labels (CLI or join token; `armada.os`/`armada.arch` reported by the agent, `armada.site` from the node's site (ADR 0050; empty = the first site, no label), `armada.` reserved), restricted nodes, `placement.require`, and `placement.spreadBy` (soft: even over a label's values, then nodes; yields to capacity); every scheduling path (scale, rollout, self-healing, evacuation, rebalancing) only picks nodes from `eligible`, and replicas on nodes that stop being eligible move like cordoned ones. Image platforms are learned from agents after a pull, kept once per revision like the digest, and restrict `eligible`; the control plane never contacts registries. Replicas reserve CPU (`resources.cpu`, default 100m, also the limit when set) and memory with no overcommit; `allocatable` subtracts what Armada keeps (100m CPU and 128Mi per node, 100m more on servers) before `pick_node`, and capacity only fits and breaks ties, never outranks the replica count (T28). A node with its own subnet takes at most `MAX_SUBNET_REPLICAS` (250; finished job attempts hold no address). A replica that has kept failing to start for a minute, outside a rollout, is replaced on another node that fits (`move_failed`, one per app at a time). A pass works out once what each app needs to know about all the replicas, again only after a change, so its cost does not grow with apps times replicas. `ReplicaSpec.cpu_reserve_millis` sets the container's CPU weight and stays out of the agent's spec hash.
- Internal ingress (ADR 0007): `<app>.internal` is served by a HAProxy `frontend internal` bound to the container bridge gateway (`armada0`) (never the private IP: NAT and load balancers make that reachable from the internet) and resolved by `armada-dns` on the same address (ADR 0053; `dns/`, std only, in the runtime pack). The agent (`agent/src/dnsprocess.rs`) runs it with `systemd-run` as `armada-dns-<hash of program and settings>` (`Restart=always`), so it outlives `armadad`, reuses a running unit, and talks to it over `/run/armada/dns/<hash>.sock` (one line per connection: `names`, `clients`, `epoch`, `state`, `drain`), sending everything again to a process with a new epoch (every 5 s); a new unit reads the old one's state (`--take-over`) before binding with `SO_REUSEPORT`, then the old one drains and stops; UDP is an epoll loop per CPU (≤4, `dns/src/udp.rs`); `runtime reset` stops the units. Without armada-dns internal ingress and DNS are off on the node. It answers only the bridge subnet and forwards other names at most 128 at a time, 16 per client address, with at most 16 TCP connections per client. Names alone within a space: each container's search domain is `internal` or `<space>.internal` (outside the spec hash), first in one merged `search` line (at most 6), and the internal frontend completes a `Host` without a dot with the caller's space (`txn.cspace`). Internal and public rules never mix; the `.internal` zone is reserved.
- Container runtime (ADR 0011, ADR 0046, ADR 0054): every node runs the supervisor runtime; `armada-runtime.service` runs `armadad runtime`, which extracts and verifies the pack and exits (on a containerd node it fails). `agent.json` `"runtime": "supervisor"`; none or `embedded` is a containerd node, on which the agent starts and removes nothing and logs why; any other value is refused. The agent (`agent/src/supervisor`, over the `host::Host` seam) calls armada-node's library in process: images in `<data dir>/node/images` (`node/src/runtime/image`: `content/blobs`, `index.json`, `layers/<chain ID hex>` unpacked and checked against their diff IDs, `pull.lock` shared per pull and exclusive to collect, `index.lock` per index change), root filesystems as overlay snapshots under `active/<key>` (`snapshot.rs`), OCI specs (`node/src/runtime/spec.rs`, `oci.rs`, seccomp's default profile, the AppArmor profile loaded when the agent starts), and bundles (`container/bundle.rs`: `rootfs`, `config.json`, `record.json` last). Containers get unique IDs per creation (`<name>-<hex>`); app containers and their members run at OOM score adjustment 0, the shims at -999, `armada-etcd`/`armada-server`/`armada-agent` at -500, so the kernel kills workloads before the node's daemons. Networking through the pack's CNI plugins run as libcni runs them (`supervisor/cni.rs`: `armada0` with a fixed MAC from `bridge_mac`, host-local IPAM on tmpfs, portmap on the private IP, firewall); every address given back has its host conntrack entries deleted right after CNI DEL (`forget_connections`, failure only logged), since isolation accepts established flows first and the address may go to another space next. `armada-shim` processes (`shim/`, std only): one per spec group (one per app and runtime pack on a node) as a transient systemd unit `armada-shim-<hash>` via `systemd-run`, socket `/run/armada/shim/<hash>.sock`, limits as `armada-runtime.service` (`LimitNPROC`/`LimitCORE`/`LimitNOFILE`/`TasksMax` infinity, `OOMScoreAdjust=-999`); subreaper, the OCI runtime's `create/start/kill/delete`, `armada-log` on fds 3/4/5, one request line per connection (`create`, `start`, `state`, `wait`, `kill [all]`, `delete`, `list`), exits 10 s after its last container, refuses a pid ≤ 1 from a pid file, keeps at most 4096 unclaimed exit codes. A shim's containers are abandoned (killed and deleted from its runtime roots) only once the shim is gone (socket ENOENT/ECONNREFUSED or unit not active), never for a timeout or EOF. Logs go through one `armada-log` (`logger/`, std only) per container: rotation at 10 MiB × 3 files, a token bucket of 1 MiB/s with 4 MiB burst per container (excess dropped, never blocked, counted in one stderr line); `armadad runtime-log` is a port of the same writer. Statistics come from cgroup files (`container/stats.rs`), dials and queue readings from containers' namespaces (`container/dial.rs`, `supervisor/native.rs`).
- OCI runtime (ADR 0056): crun is the only OCI runtime; the pack carries no runc since the release after v0.1.0-alpha.44. `node/src/runtime/container/oci.rs` (`OciRuntime`: `of_record` reads a bundle record's `runtime`: `crun`, or `runc`/none for a container runc created under an older release, an unknown name refused; `for_create` = crun, refusing runc; `root` = the runtime's `--root` under the shim's state, `/run/armada/shim/<shim>/crun`, and runc's old `.../runc`). Bundle records name `"runtime":"crun"`; the agent (`agent/src/supervisor`: `Shims.crun`, `Shims::root(group, rt)`) sends `create ID BUNDLE LOGDIR crun` and runs exec sessions, probe and queue commands, and system execs with crun (`exec::ExecRequest`/`SessionRequest` `program`, always with `consoleSocket`; texts `exec: crun exec: fork/exec ...`, `exec: crun exec did not start the process`). `armada-shim serve SOCKET STATE CRUN ARMADA-LOG` (`create` takes no word or `crun`). A gone shim's containers: crun's ended with crun, and every container runc's state (an alpha.44 shim's) names ended through its cgroup with its state removed (`Request::abandon_root`, `abandon_runc`, `Request.cgroup_root`). The pack carries crun's static `-disable-systemd` release build (Armada's cgroup paths are cgroupfs paths, `/armada/<id>`, and it never asks for `--systemd-cgroup`), `daemon/src/pack.rs` `BIN_CRUN`, and `armadad runtime --bin-dir` needs crun. crun's exec with a terminal runs with `--console-socket <exec dir>/console.sock`: `armada-node` binds it through the directory's descriptor (`console_listener`), takes the container's terminal master over SCM_RIGHTS (`await_terminal`, `recv_terminal`), copies and resizes through it, and copies crun's own stdout and stderr to the caller's output (`node/tests/exec_console.rs`; the conformance suite checks it on crun); crun's `kill --all` of an ended container succeeds and it writes pid files in place (ADR 0056 lists the arguments). Containers runc created (`agent/src/runcleft.rs`, ADR 0056 "runc leaves the pack"): `runtime::Container.oci_runtime`/`Member.oci_runtime` from the record, `Container::on_runc` = it or a member. The supervisor ends one without runc (`is_runc`, `end_runc`: `node/src/runtime/container/cgroup.rs` `end` on the spec's `cgroupsPath`, else `/armada/<id>`, any other path refused: `cgroup.kill`, then SIGKILL to every pid in `cgroup.procs` of the tree each round until none is left (10 s), then the cgroups removed deepest first; `kill_all` replaces `kill --all`, `stop_runc_container` SIGTERMs through the shim first when there is a grace) and removes it (`remove_runc_container`: ended, the shim's `delete` tried (an alpha.44 shim fails it without runc; the shim is stopped, `Shims::stop`/`Request::stop`, once no record of its group is left), runc's state dir removed, then network, bundle, root filesystem, files, logs as `remove_files`); exec refuses it (`crun_of`). Each pass `runc_pace` picks, per app, one replica whose running container runc created (`RuncLeft.recovering` by app, in memory, `Recovery` with `Step::Draining`/`Ended`; apps in parallel): when the app has another ready replica (`other_ready`: this node's probes, or `served_elsewhere` in the proxy configuration's backends) it is reported starting with its old container and no address (`runc_draining`) and ended `DRAIN` (5 s) later (a task triggers that pass), else ended at once; ending is `end_runc_replica` (stop with no grace, remove, restart note `RUNC_NOTE`, logged once per container), and the pass starts it again on crun, reported starting meanwhile; the app's next waits until it runs and is ready, at most `READY_WAIT` (5 min, logged); after a restart, a crun replica started within `READY_WAIT` and not ready counts as its app's recovery; a stopped runc container is ended at once; running job attempts are left to end; `move_proxy_to_crun` runs `Proxy::on_runc`/`move_to_crun` in a task from the first pass (one at a time, `BACKOFF` 10 min doubling to `MAX_BACKOFF` 2 h): the HAProxy driver's `move_to_crun` takes its lock, reads the load, has the engine `replace_on_crun` (a new container from the files on disk beside the old one, both listening with SO_REUSEPORT; SIGUSR1 to the old one, stopped after `RETIRE_WAIT` 30 s; a new one that does not stay up falls back to `start_now`), then reloads. Nothing reports the count (`RuntimeStatus` is gone, its `UsageReport`/`NodeStatus` fields reserved). Installing a pack removes the other packs' directories: shims and every program are named through `runtime/current/bin`, so an older pack's shim runs the installed pack's programs.
- Admin config (ADR 0027; `client/src/config.rs`): `armadad init` writes `SYSTEM_PATH` (`/etc/armada/admin.config`, root:`armada` 0640, `/etc/armada` gets o+x only); `default_path` = `$ARMADA_CONFIG`, else `~/.armada/config` if it exists, else the system path if it exists; a config is read with group read only when root-owned, 0640, and group `armada`. `ssh` (ADR 0048): every connection runs the user's `ssh -o ExitOnForwardFailure=yes -W ADDR -- DEST` (`client/src/dial.rs`; ssh's last stderr line in errors; `check_ssh` refuses option-like or shell destinations; the config's servers only). Saving keeps a shared file shared; the installer creates the group. Run through sudo, init and `server join` add `SUDO_USER` to the group (`join_admin_group`: `usermod -a -G`, else `gpasswd -a`, else BusyBox `addgroup`; failure only warns) instead of copying the file to the home, and init names the first user (cluster-admin) after them; each server renews the user certificate in its own shared file (as root from the default data directory, at start and every 12h once due, new key, recorded so a deleted or replaced user stays out); an unreadable shared file says whether the account is outside the group or joined after the session started (`group_advice`).
- Access control (ADR 0033; `server/src/access.rs`, `rbac.rs`, `grpc.rs`, `guard.rs`, `store/src/access.rs`): principals are users (one year) and services (90 days); records under `users/` and `services/` hold role grants (role + space, "" = cluster: `cluster-admin`/`space-creator` cluster only, `deployer`/`admin` one space and never `default`, `viewer` either) and allowed node labels. Users keep the serial a replacement recorded and a cutoff (`user_allowed`): certificates issued in a later second than the record was written; deleted = tombstone. Renewing one's own certificate signs, then checks the caller and audits in one transaction, rate limited per name. A name with no record is cluster-admin only for a certificate issued before `meta/user-cutoff` (schema 14) or while the keyspace is older; a keyspace created at 14 refuses every such name, so a user lost in a restore is refused. Everything that signs a user certificate outside the API records the name first (cluster-admin unless on record): init, `armadad user renew`, and `armadad server join` (recorded by the leader; no config written without it). Services: recorded serials. Every call is authorized before its handler from the certificate's identity (`method_access`, `method_needs`: view/deploy/admin space levels, creating spaces, self; anything missing is cluster-admin only, tested over the whole service descriptor); streams recheck every 5 s (`STREAM_RECHECK_EVERY`) and at the certificate's expiry, and a refusal ends the stream with that error. Nobody deletes themselves or drops their own cluster-admin. Creating a space makes a space-creator `admin` of it in the same transaction; deleting one takes every role in it back; for non-cluster-admins events and history searches leave out what a space's apps left before the space was created. Non-cluster-admins get no nodes and no cluster events.
- Platforms: Armada runs on Linux only (linux/amd64 and linux/arm64 releases); only the `armada` client also builds for macOS (darwin archives, built on a macOS runner, client-only `install.sh`); Linux releases also carry a client-only archive (`armada-client_<version>_linux_<arch>`) that `install.sh` uses with `ARMADA_CLIENT_ONLY=1`, and a full install puts both binaries as separate files; Windows has no native client, the docs point to the Linux client in WSL 2. Binaries (ADR 0027): the daemon (`daemon/`, `armadad`) holds every command that runs on a machine and reuses the client's command framework (`armada_client::cli`); the client (`client/`, `armada`) only talks to the API. Removed `Hello` fields are reserved in the proto.
- Command line (ADR 0032, ADR 0052; `client/src/cli`, `client/src/commands`): `armada NOUN VERB` and nothing deeper; the root holds only nouns and `version`, listed in four groups (Apps, Cluster, Access, Monitoring); no old names or aliases beyond `ls`/`rm` and plural nouns. `app deploy` and `job deploy` build a spec from flags (or read `--file`, with `--vars`/`--var`), validate it after export, and send `DeployRequest` with `must_create`, or `must_exist` + `base_revision` (the revision `GetAppSpec` returned; flag updates only), so a change in between is refused; `--diff` prints a line diff of the exported specs and deploys nothing. `app show`/`job show -o yaml` print `GetAppSpec` as is. `app list` follows `ListApps`' `next_page_token`; `cluster status` is `ClusterStatus`. `Status` with an app returns that app and no nodes, reading only its own replicas and domains, and every replica and the servers only when its placement message compares with them. Other read paths (`ListVolumes`, `ListJobs`, `ListSpaces`) stay in a few batches whatever the cluster's size. The space: `--space`, else `ARMADA_SPACE`, else the client config's (`space use`), else default; `-A` spans spaces in lists. Output: lists print a table only, actions one line of what happened, `-o json` (protojson) on everything that prints data. Argument errors name the missing placeholders of the Use line (or how many are too many; never an argument's value, which may be a secret) plus the usage line, flag errors point to `--help`, and a noun's help lists each verb with its arguments. `app exec` runs `/bin/sh` without a command and sets `-i`/`-t` from the terminal unless given. Unknown verbs print a hint (`verb_hints`: `app scale`, `secret get`, ...); `secret show` of a missing secret names the space's secrets. Completion (`cli/complete.rs`): each positional argument's completer comes from its Use placeholder (`arg_kinds`, `placeholder_kind`), flags (`--replica`, `--container`, `--to`, `--run`, `--space`, `--node`, `--role`, `--user`, `--service`) likewise, each asking the cluster within 5 s; it never offers a secret's value. Status messages are printed with control characters replaced (line breaks kept); the leader relays agents' volume errors cleaned (`clean_message`).
- Starting replicas (ADR 0011; `agent/src/agent.rs`): the pass decides without starting anything, then `start_pending` starts at most `MAX_CONCURRENT_STARTS` replicas at once, each image pulled once per credentials for that set of starts. Pulls (`node/src/runtime/image/pull.rs`, `registry.rs`, `http.rs`): a digest-pinned image on the node is used without the registry only when it was pulled with the same credentials key (SHA-256 of registry, user, password, or `anyone`), else the credentials are checked first; every registry, redirect, and token request goes over HTTPS only, the other URLs a manifest lists for a layer are ignored, at most 10 redirects, an HTTPS proxy only when the environment names one, and no link-local, unspecified, or multicast address is dialled (T83); a blob a pull did not download itself is used only when an image pulled with the same key holds it, else fetched again and checked; an image is kept only once every layer decompresses to its config's diff ID (`check.rs`), since unpacked layers are found by diff IDs alone. Collecting unused layers and blobs waits for pulls in flight. Every start report interval the agent applies the firewall for finished starts, applies proxy changes, and reports the rest; a replica starting for the first time is left out, and one whose container is being recreated (crash, liveness, spec change, machine restart) is reported `starting` with no address and its old container ID from the first report, sent before any start, so its old address usually leaves the proxies before the node hands it to another container (nothing waits for the proxies; a quicker start is caught by `claimed_twice`, and the firewall and internal frontend still check the caller). A replica's `AddressConflict` (and every other condition of an app or job) ends when it is deleted (`end_app_conditions`). Every `DEFAULT_IMAGE_PRUNE` (10m) the agent removes images no container uses, not named by the assignment, and not pulled within `IMAGE_PRUNE_GRACE` (1h).
- Exec (ADR 0015; `server/src/exec.rs`, `agent/src/side/exec.rs`): `armada app exec` opens `AdminService.Exec`; the server picks the replica (`find_replica`: the ID or its short name, `short_replica`; errors list the app's replicas; `Logs` resolves `--replica` the same way, passing an unknown one through only to a history search) or a running, ready one of the serving revision, checks `--container` against the replica's revision (`check_container`: NotFound naming the containers, exec refuses init containers), audits the command's name (never its arguments), and offers an `ExecRequest` over the node's Connect stream; the agent checks the replica is its own, then opens `AgentService.ExecSession`, which the server accepts once and only from that node (`ExecRouter`, like `LogRouter`). The process copies the container's own process spec, so it keeps every security setting. `check_exec_command` bounds commands (64 args, 4096 bytes, no NUL) on every hop; 32 KiB per message, `MAX_EXEC_SESSIONS` (8) per agent, 30 minutes idle. Sessions run in armada-node (`runtime exec`, `node/src/runtime/container/exec.rs`; the agent's `supervisor/exec.rs`): the request on fd 3, a control socket on fd 4 (resizes, kill, abandon), the caller's input and output on fds 5/6/7; it writes `process.json` from the bundle's `config.json` with only args/terminal/consoleSize replaced, starts the runtime on pipes or a pty (`PR_SET_PDEATHSIG` SIGKILL), answers once the pid file names the process (or not after 10 s), and once the process exits keeps copying output while it moves, ending once none moved for `DRAIN_GRACE` (2 s), since a child the command left can hold the output open (a terminal after `TERMINAL_DRAIN_GRACE`); output cut by the caller's deadline is an error with the exit code, never a silent success; the cleanup kills within 5 s, so queue and probe commands end within their timeout plus a few seconds; a session's own length is unbounded. Never log or audit exec arguments.
- Log history (ADR 0043; `agent/src/supervisor/history.rs`, `logger/src/search.rs`): the runtime writes `<logs>/history/<id>.meta` (app, replica, revision, container) for app containers and members; rotation moves the file it would drop and removing a container moves its files into history as `<id>.<unix ns>.log` (deleted without meta). Searches read the app's live files then history, newest first, within a byte budget, keeping the newest entries in the window containing the grep (plain text, case-insensitive), through armada-log's `search` mode (files on stdin, `INDEX LINE` out, then `end ok|budget|timeout BYTES`) or read in the agent when the grep is not ASCII or armada-log is missing; `prune_logs` drops files past retention, then the oldest past the size (`default_history_bytes`: 10% of the file system, 64 MiB–5 GiB), and meta of removed containers. The agent announces `Hello.log_history`, answers searches (1 GiB, 30 s, ≤ 5000; `MAX_SEARCHES` 2 at once) and prunes every minute with `Assignment.logs`. The leader stores `meta/logs` (`--log-retention` 1h–90d, `--log-max-disk` 64Mi–1Ti, no restart), sends it in every assignment, and fans a search with `since` out to every node with a log history (`server/src/logs.rs`), keeping only entries of the app's replicas (`<app>-r<n>`/`<app>-j<n>`) inside the window, ≤ 32 MiB per node, and only replicas placed on the answering node (`placements/<replica ID>` records written with the replica, plus the live replicas; pruned hourly past the log retention + 1 day), merges by time, keeps the newest `limit` (500, ≤ 5000), then notices; 4 searches at once, 2 per caller; live logs take one of 128 slots, 8 per caller (`CallerSlots`, `ResourceExhausted`), each agent streams at most `MAX_LIVE_LOGS` (32, a busy notice beyond), a tail keeps at most 4 MiB, and with `follow` only new output follows. The grep also filters `-f`/tail output on the node (tail counts matches), live entries carry their time (else the leader's receive time), and following a whole app relays replicas that appear later (every 2 s).
- Log export (ADR 0044; `agent/src/side/logexport.rs`, `logger/src/export.rs`): Loki push JSON (labels app/space/container/stream/node/source, replica/revision as structured metadata) or OTLP/HTTP JSON (resources per replica container), gzipped, bearer or basic auth, `X-Scope-OrgID`, no redirects, errors without the token; the endpoint is https, or http to a private IP, with no userinfo or query. The leader keeps the export in `meta/logs` (token sealed as scope `cluster`/`log-token`; `cluster update --log-export/--log-endpoint/--log-export-user/--log-export-tenant` go together, the CLI fills the ones not given; `--log-token` from a file or stdin) and opens the token into `Assignment.logs.export`. Cursors per container (inode, offset, time) live in `<logs>/history/export.json` (a new target starts existing containers at their end, a file gone falls back to time, written only on change); armada-log's `export` mode (plan on stdin as tab-separated `c`/`f` lines, out `body LEN` + JSON per request, `cursor`, `end SIZE`) reads the files and renders the requests, the agent moving the cursors only after it ends cleanly. The loop runs every 2 s, 8 MiB per round, batches of 2000 entries or 1 MiB, backoff to 1 min, at least once, and reports `UsageReport.log_export`; the leader keeps a `LogExportFailing` condition per node.
- Alerts (ADR 0045; `server/src/alert.rs`, `alerts.rs`): webhook JSON, Slack `text` (escaped), Discord `content` with mentions off and Markdown escaped, Telegram `sendMessage`, email over SMTP with TLS on 465, STARTTLS otherwise, plaintext only to private IPs, PLAIN auth only over TLS, headers from checked addresses; no redirects, no environment proxy; errors without the secret. - Usage (ADR 0016): agents sample running replica containers every 10 seconds (`agent/src/usage.rs`; cgroup v2 statistics, memory without inactive file pages) and send a `UsageReport` (CPU as millicores over the interval) on the Connect stream, apart from replica reports. Memory kills: the cgroup's `oom_kill` count makes a crash say "out of memory", and a rise while the container runs becomes an `OutOfMemory` event (own node only, at most 8 per report). - Metrics (ADR 0017; `server/src/metrics.rs`): only the leader serves `GET /metrics` on `--metrics-listen` (private address, TLS 1.3 with the API's server certificate, client certificate required; only `metrics:` identities and principals with cluster-admin through). - Events (ADR 0018; `server/src/events.rs`): only the leader records them (`record`), from transitions it already sees (reconciler, agent replica reports, API calls, ACME callbacks). - Jobs (ADR 0019; `server/src/jobs.rs`, `triggers.rs`, `agent/src/job.rs`): `kind: job` specs are stored as apps (revisions pin secrets) but with no rollouts (deploy makes the revision active at once; rollback refuses; Status leaves them out). The leader's `reconcile_jobs` schedules (latest due fire, written with the run so a fire runs once; >1h late is `Missed`; `concurrency` forbid/replace), places attempts only on eligible nodes whose agent announced `Hello.jobs`, ends attempts on exit, start failure, lost node, or timeout, retries with backoff, and prunes to `history` (containers kept 24h, done replicas reserve nothing). The agent never restarts an attempt, reports `finished` + `exit_code`, and stops but keeps a done attempt's container, its address released. Tasks (`tasks`/`parallelism`, ≤ 100, not with `trigger`): each task is retried on its own, pending ones start in index order while fewer than parallelism run, the run fails once a task has no retries left and succeeds when all did; replicas are `<job>-j<run>-t<task>-<id>`, env `ARMADA_JOB_TASK`/`ARMADA_JOB_TASKS` only with tasks (schema 12). Runs are at least once. Queue triggers (ADR 0040): `trigger.queue` (`redis`/`rabbitmq`, `urlSecretRef`, `perRun`, `pollingInterval`, `parallelism`; not with `schedule` or `concurrency`; refused without a cluster network). Each pass `place_queues` picks every job's probe node in fair order (one job of each space per round) with `probe_node` (rendezvous hash over eligible nodes with a subnet that run jobs, are not lost, announced `Hello.queue_sandboxes`, and hold fewer than 64 sandboxes), puts a `QueueSandbox` (URL from the pinned secret) in that node's assignment, adds the sandbox's address to the network's endpoints as the job's, and, once per fresh reading, creates ⌈length÷perRun⌉ (≤ parallelism) minus active runs with trigger `queue` (`QueueTriggered` event); `QueueUnread` and `QueueReadFailed` conditions say why nothing was read (the agent's reason kept only as one of the fixed texts). - Autoscaling (ADR 0020, ADR 0034; `server/src/autoscale.rs`): `scale.rules` (`http` concurrent, `cpu`/`memory` utilization of the reservation, `queue`, `schedule`). Agents add proxy load (HAProxy `show stat` scur+qcur mapped from slots; only busy replicas are sent, too many entries make the load unmeasured; Runtime API replies past 128 MiB are errors, never cut) to their usage reports for every replica their proxy routes to; the leader sums it across nodes, CPU/memory count only from a replica's own node. Every 15 s `decide`: average over ready replicas, ⌈ready×avg÷target⌉, 10% tolerance, max of rules, up at most 2× ready, down only to the highest recommendation of the last 5 minutes (a new leader waits a full window), frozen during rollouts; writes are conditional (count and revision unchanged, within bounds); deploy/rollback keep the count within the new bounds. Window state is memory only. Queue rules (`queue` with a `command`, `redis` with `urlSecretRef` + `list`, `rabbitmq` with `urlSecretRef` + `queue`; each with `length` and `min` ≥ 1) reach the agent as `ReplicaSpec.queues` (URL decrypted from the pinned secret, outside the spec hash); the agent (`agent/src/side/queue.rs`, every 15 s) reads each from the lowest-ID ready replica of its app on the node (10 s, at most 32 per pass, 4 at once): `queue` runs the command like a command probe (64 bytes, whole number 0..2^40, arguments and output never logged), `redis`/`rabbitmq` go through armada-node's readers (`node/src/queue`: minimal RESP with AUTH/SELECT/LLEN; AMQP 0-9-1 passive declare with PLAIN, AMQPLAIN, or EXTERNAL; Armada's own TLS, so URL certificate paths are never read; errors never carry the URL or broker text and map to fixed texts) from the replica's network namespace, the broker's name resolved from inside it (`agent/src/side/dns.rs`); failures are logged once per change. The leader keeps readings per node (own node only, bounded) and asks for ⌈largest length ÷ `length`⌉ per rule. `schedule` rules (`schedule` + `timeZone` like jobs, `duration` 1m–7d, `replicas` 1..max, up to 8) are evaluated from the spec each pass: an open window raises the count, keeps an app that scales to zero up (`schedule_open`) and starts it from zero (`schedule_wake`), and is never held back by unmeasured metric rules; closed with only schedules = `scale.min`. `AutoscaleRule.until` says when an open window closes.
- Scale to zero (ADR 0021): `scale.min: 0` needs rules and ingress; a first deploy starts 1. - Traffic splitting (ADR 0022): `revisions.mode: multiple` (needs ingress, not with `min: 0`); traffic lives in the app record, not the revision, so weight-only deploys make no revision; deploys make the revision current with no rollout; `SetTraffic` (`armada app traffic`) keeps labels; for non-cluster-admins, revisions added to the traffic pass the stored-spec placement and NFS checks of a rollback; `Rollback` refuses; traffic revisions are never pruned. - Volumes (ADR 0023; `server/src/volumes.rs`, `agent/src/files.rs`, `agent/src/side/volume.rs`, `node/src/volume`): `volumes: [{name, path, owner}]` (at most 8, paths like secret files, no host paths) force exactly one replica (no rules, no `min: 0`, single mode, not jobs). The agent mounts `<data dir>/volumes` onto itself `nosuid,nodev` at start (failure disables volumes) and creates `<data dir>/volumes/<app>/<name>` (0700, root-owned 0700 parents, chowned to `owner` on every start when the agent is root) and mounts it `rbind,rw,nosuid,nodev` (relabelled for SELinux on every start). Agents announce `Hello.volumes`. Creating a replica binds the revision's volumes to its node in the same transaction (`volumes/<app>/<name>`) and refuses other nodes. `reconcile_volume_app` replaces the normal rollout when the target revision has volumes: recreate (a new replica only once every other replica of the app is gone; during a rollout it is first created held when the node's agent announced `Hello.held_replicas` and has room for both (`holds_at`): the agent (`agent/src/hold.rs`) pulls its images in the background and starts nothing, the old replica is retired once the held one reports `pulled`, then `release_replica` lifts the hold), pinned to the volume's node (cordoned allowed, lost = `VolumeUnavailable`, split = `VolumesSplit`), no evacuation or rebalancing. Sizes are measured every minute (memory only; `armada volume list`, `armada_volume_used_bytes`). Volume contents are not in `armadad backup`. Schema 5.
- Volume backups (ADR 0041; `node/src/volbackup`, `server/src/backups.rs`, `failover.rs`): `volumes[].backup` (`every` 5m–7d or `schedule`+`timeZone`, `keep` (a number = `last`, or last/hourly/daily/weekly/monthly ≤1000), `urlSecretRef`, `keySecretRef` (never in `envFrom`), `stop`). Targets (`target.rs`): `https://KEY:SECRET@host/bucket[/prefix][?region=]`, `http://` only for private IPs, never loopback/link-local/unspecified/multicast (also refused at dial time), errors never repeat the URL; `check_backup_targets` (in Deploy, Rollback, SetSecret): a private-IP bucket needs cluster-admin unless the revision the app is heading to already has it. S3 path-style with SigV4, dialled directly, never through an environment proxy (`s3.rs`). A repository per volume at `<prefix><app ID>/<volume>/` (`repo.rs`: `config` with repo ID and key check; `chunks/<2>/<64 hex>`: content-defined chunks 512 KiB–8 MiB from a keyed gear table, named HMAC-SHA-256 of the plaintext, zstd then AES-256-GCM with the object name as AAD; `snapshots/<UTC ms time>-<8 hex>` sealed manifests), keys by HKDF-SHA-256 from the key secret salted with the repo ID; a backup lists chunks once and uploads missing ones (32 at once within 64 MiB) then the manifest; a restore checks each chunk against its name, reading ahead 32 within 64 MiB; prune deletes unkept snapshots, then unreferenced chunks older than 1h, only after reading every kept manifest. The agent runs them on the volume session (`OP_SNAPSHOT`/`OP_SNAPSHOTS`/`OP_RESTORE_SNAPSHOT`, a lock per volume; the keep policy counted in a zone table it sends, `zone_table`); `Hello.volume_backups`. The leader's `backup_loop` (every 30 s) starts due backups (`backup_due`; retry after min(5m, every)), at most one per volume and one scheduled per node, from the revision's pinned secrets; `VolumeBackupFailed`/`VolumeBackupUnsupported` conditions; `ListVolumeSnapshots`, `CreateVolumeSnapshot`, `RestoreVolumeSnapshot` (when the volume's node is gone, a connected node that may hold the secrets: ready and allowed for the serving and target revisions); metrics `armada_volume_backup_*`. Failover: `volumes[].failover: restore` (needs `backup`, all volumes or none). Assignments set `ReplicaSpec.fence_after_seconds` = node-lost timeout ÷ 2 (≥1 s); the agent (`agent/src/fence.rs`) stops such replicas once cut off from the control plane that long (reported exited; before the first assignment by the `armada.fence-after` label) and starts them again at once on contact; the fence time is outside the spec hash. The leader's `fail_over` (one at a time per app, retry after 5 min) picks an eligible, connected node with room, restores every local volume's latest backup there (NFS volumes skipped), refuses to bind if the old node reconnected, then binds each with actor `armada:failover`; events `VolumeFailedOver`/`VolumeFailoverFailed`.
- Control plane backups (ADR 0051; `server/src/cpbackup.rs`, `daemon/src/backup.rs`): settings in meta `control-plane-backup` (every or schedule + time zone, keep, the bucket for display, URL and key sealed as `cluster`/`backup-url`, `backup-key`, versioned; set through `SetClusterConfig`, all four needed to turn on, checked like `volumes[].backup` with a key of at least the minimum length; audited as `cluster.backup` with markers only; no restart); state in meta `control-plane-backup-state`. - Init containers and sidecars (ADR 0038): `initContainers`/`sidecars` (at most 4 each, names ≤30 and not `app`, own env with `secretRef`, no app env/`PORT`; `volumes`/`secretFiles` name the app's). - Spaces (ADR 0026; called projects before schema 11): records under `spaces/` (`default` always exists, has no record, cannot be removed; a space is deleted only when nothing keyed by its app IDs is left). - Cluster network (ADR 0025; `server/src/network.rs`, `store/src/network.rs`, `agent/src/clusternet.rs`, `node/src/net`): the `network` record (mode `plain`/`wireguard`/`mesh`, cluster CIDR) is set by `init` (`--cluster-cidr`, only before any node exists); clusters created earlier have none and keep one container subnet everywhere. Every new node record gets the lowest free /24 (`new_node_network`, in the same transaction; a private IP inside the CIDR is refused, and any private IP that is not IPv4: "the cluster network carries IPv4 only"), returned by the join and written to `agent.json` `containerSubnet`, so `armada0`'s gateway differs per node; `agent.json` `network` records the mode (an unknown mode refuses to join). The leader sends every node `Assignment.network` (`build_network`: mode, CIDR, every node with a subnet); the agent applies it before the proxy on every pass. armada-node (`net/plan.rs`, `apply.rs`) re-validates the peer list and sets up `armada-net`: VXLAN 4789/VNI 7027 on the private IP, no learning, static FDB + neighbour entries, tunnel end = subnet network address with MAC `02:42:<ip>`, onlink routes per peer subnet, stale entries removed; iptables (`iptables.rs`, `rules.rs`) `ARMADA-NET-IN` (port only from peers), `ARMADA-NET-FWD` (tunnel ↔ `armada0` only; NEW non-DNAT connections into `armada0` not from the tunnel dropped), raw `ARMADA-NET-PRE` (`spoof_rules`, first in PREROUTING since the CNI plugins accept containers' packets in FORWARD first: UDP from `armada0` to a peer's tunnel port, sources in the node's own subnet arriving on anything but `armada0` (the node itself over `lo` returns first), and tunnel sources outside the CIDR, dropped; the DNS server, internal frontend, and isolation trust a subnet source as one of the node's containers), `nat POSTROUTING -o armada-net RETURN` (no masquerade), `ARMADA-NET-MSS` (TCP MSS clamped to the path MTU). MTU = uplink − 50 (min uplink 1280) on the tunnel, `armada0`, and CNI. Routing and WireGuard over netlink encoded by hand (`rtnl.rs`, `wgnl.rs`, `netlink.rs`; no crates), kernel WireGuard only: a node whose kernel lacks it fails the pass (`ERR_NO_KERNEL_WIREGUARD`). Doctor (`net/diagnose.rs`) and `runtime reset` (removal) use the same code. `wireguard` mode: the agent loads or makes `<data dir>/network.key` (0600, redacts itself, not in backups) and sends the public key in `Hello.network_key`; the server keeps it only when well-formed and refuses a key another node holds; peers without a key are skipped; changes are applied only where they differ (`peer_changes`, 25 s keepalive), port 51820, MTU uplink − 80, the port open only to peers' private IPs; doctor checks handshakes (< 3 min). No published ports: with a cluster network and a node subnet, replicas run with no port and report `<container IP>:<port>` (outside the spec hash); the node's own /24 except .0/.1/.255 is a valid replica address, and HAProxy counts subnet addresses as local. Schema 6.
- Isolation (ADR 0026; `node/src/net/policy.rs`, `nft.rs`, `kernel.rs`): agents report every replica's container IP (only the node's own /24 kept); the leader sends `NetworkConfig.endpoints` (address + app ID; done replicas and addresses two apps claim left out) and `isolate_default` (set by `armada space update default`, cluster-admin only); the agent merges its own containers each pass and right after a start and gives them to armada-dns (internal names only within the asker's space, nothing for unknown addresses; a lookup of an internal name from an address not known yet waits up to 3 s for the agent to name it, since a container runs before the agent hears of it; the proxy's callers and the firewall are set before the resolver's clients, so a name resolves only once the internal frontend accepts the caller; before the agent's first proxy configuration every such lookup waits up to 10 s, since containers keep running across an agent restart). The bridge has IPv6 turned off before it comes up (doctor's `isolation` check fails otherwise), since the rules are IPv4 only. nftables, encoded by hand on a raw netfilter socket (no library, no `nft` binary): tables `ip armada` and `bridge armada`, changed in place in one transaction when only apps or open containers differ (set elements in messages of at most 256, since netlink attribute lengths are 16 bits; one acknowledgement per transaction, so 10,000 apps do not overflow the socket), rebuilt when anything else does: established/related first, node sources .0/.1 pass, cluster→cluster through a `dst` verdict map to a per-app chain (source set), unknown destinations dropped; the bridge table on `armada0` passes ARP and drops non-IPv4; for this node's sources not in `open` (isolated spaces; unknown = isolated): forward drops private/shared/loopback/link-local/multicast ranges and `nodes`, input allows only DNS on the gateway, TCP 80/443, and the ports of internal TCP apps on the gateway. Internal frontend check: the agent also gives the merged list to the proxy (IPv4 in the node subnet, valid app IDs, at most 4096, sorted, written 0600 to `clients.map` and swapped with `prepare map`/`add map @ver`/`commit map`, no reload); `frontend internal` sets `txn.cspace`/`txn.capp` from `src,map_ip` and every internal route requires the app's space (and, with `ingress.allow`, the app or one of the listed apps of its space), only when the node has a subnet; unknown callers, the node included, get 404. `ingress.allow` (at most 32, same-space names, not self) is enforced only in HAProxy; direct traffic stays same-app only.
- Mesh, sites, and NAT (ADR 0049, ADR 0050; guide `docs/guides/more-than-one-site.md`): mesh mode (`init --network mesh [--endpoint IP] [--mesh-cidr CIDR]`, default `10.122.0.0/16`): a node's private IP is its mesh address and its endpoint its public IPv4 address (`Hello.endpoint`); peers are reached at their endpoints, each allowed its mesh /32 and subnet, an endpoint WireGuard roamed to kept while its handshake is fresh; the mesh address sits on `armada-net` with a route per peer, the WireGuard port opens to everyone, peers' traffic to the mesh address is accepted (`ARMADA-NET-MESH`), the mesh range is dropped anywhere but the tunnel, the uplink is found from the endpoint, and the last peer list is kept in `mesh.json` (not backed up) so the tunnel comes up before the control plane. Init takes the first mesh address and brings the tunnel up alone before etcd; a public join address means a mesh: `join`/`server join` send a key and endpoint (`--endpoint`, else detected), get a mesh address and the peer list, and bring the tunnel up before writing `agent.json`. The leader binds the join listener to its endpoint only while a join token is open (checked on create/redeem and every 5 s; connections from addresses tokens do not name (`join-token --from`) are closed before TLS); such tokens last 10 minutes by default, at most an hour. Switching modes (`cluster update --network`, plain ↔ wireguard only; refused while a connected agent cannot switch, with a remote peer, or while any node has a site): steps prepare and move, advanced by the leader (`advance_switch`, recheck every 10 s) once no node waits (`switch_progress`, from the nodes' usage reports); the target transport runs on `armada-next` beside `armada-net` (prepare: peers and a /32 route to each peer's tunnel address, probed every 5 s from the node's tunnel address and counted only when the reply arrives on `armada-next`; move: every route on `armada-next`; done: renamed to `armada-net`, or removed when given up); the current mode gives a switch up during prepare; events `NetworkSwitchStarted`/`Moving`/`Switched`/`GivenUp`; the agent writes the finished mode to `agent.json`. Sites: a peer of another site is `remote` and kept only with a key and an endpoint; plain clusters reach remote peers over `armada-wg` (removed when no peer is remote), wireguard clusters over `armada-net`; a remote peer is allowed its node /32 and subnet, routed from this node's address, accepted to it, its address dropped on any other interface; the WireGuard port opens to everyone once a peer is remote; the tunnel MTU takes the smallest uplink towards remote endpoints; `mesh.json` is kept whenever a peer is remote. Joining from another site: a leader with an endpoint also opens a join listener there, gated like the mesh one but only for tokens of another site (which need the endpoint; `FailedPrecondition` without), answering with the peer list. Machines with no private network join with `--no-private-ip` and get a mesh address from the recorded mesh range (`cluster update --mesh-cidr` before the first such join; no overlap with the cluster CIDR); a meshed node holds its address on its WireGuard interface and has no VXLAN device. Doctor: `network-sites` (handshakes on `armada-wg`), `sites` (a remote peer's address inside one of the machine's own networks). Nodes behind NAT: `join --endpoint none` or `armadad endpoint set none` (not on servers) sets agent.json `behindNat`; the leader picks a relay per site (`site_relays`: key, endpoint, not behind NAT, ready, not lost, not cordoned; the admin's pin (`armada node relay`, one per site, `RelayChosen`/`RelayCleared` events) while it qualifies, else a rendezvous hash of site and node); peers behind NAT have no endpoint (WireGuard learns it); a list claiming a relay behind NAT or two relays in one site is refused; pairs behind NAT that cannot reach each other go through the relay (`relay_through`, `pair_relay`: the relay of the pair's site that sorts first, else the other's, else the first site with one), which forwards between their subnets; pairs with no relay are unreachable. A node behind NAT finds its uplink by the route to an internet address; `join --mtu` (1280–9000) caps the uplink MTU. Doctor `relay`. Unreachable peers: the agent names WireGuard peers with no handshake for a while since they were configured (`stale_peers`, ≤ 32, none during a switch), and the leader keeps a `PeerUnreachable` condition per node (an alert warning). Key rotation: `armada node rotate-key NODE` (cluster-admin, audited; needs a connected agent that announced it) asks the agent (`rotate_network_key`, one at a time) to write a new `network.key` (atomic, 0600) that the devices take on the next pass; the agent sends the new public key and the leader records it (`network_key_changed`; refused when another node holds it), records `NetworkKeyRotated`, and triggers a pass. Status: node endpoint, behind NAT, relay, pinned; `node list` states `behind-nat`/`relay`.
- Internal TCP ingress (ADR 0039): `ingress.protocol: tcp` only with `type: internal`; no routes, domains, sticky, cors, IP rules, timeout, `min: 0`, `http` rules, or multiple mode; reserved ports refused (22, 53, 80, 443, 2379, 2380, 4789, 7443, 7444, 7445, 7446, 7480, 8404, 51820). A second app of a space on a port is refused (other spaces may share it); TCP needs the cluster network (`FailedPrecondition`). The proxy configuration gives a TCP app a plain backend (local-first, no health path) and a TCP route (port, backend, allowed callers), no HTTP rule; URL `tcp://<app>.internal:<port>`; validation (`valid_tcp`) checks ports, counts, an existing backend with no HTTP rule or settings, one per space and port, callers of the space. The renderer writes `defaults tcp` (mode tcp, tcplog, client/server timeouts 1h), one `frontend tcp_<port>` per port bound only to the gateway, `tcp-request connection set-var(sess.cspace|sess.capp)` from `clients.map`, `sess.route` per backend of the caller's space (and its `allow`), `reject unless` found, `use_backend %[var(sess.route)]`; TCP backends `balance leastconn`, local-first through `tcp-request content`. The driver leaves out ports another program listens on (`busy_tcp`, `held_tcp` from `/proc/net/tcp{,6}`), so a reload never fails on them. The leader sends `NetworkConfig.tcp_ports`; the agent re-checks them; nftables set `tcp` and, only with ports, `isolated, daddr gateway, tcp dport @tcp, socket wildcard 0, accept` (never a wildcard listener). CLI `--protocol http|tcp`.
- Client address headers (ADR 0035, ADR 0036, ADR 0037; `node/src/proxy/render.rs`): `frontend https` removes the client address headers unless the connection comes from a trusted proxy, and `X-Forwarded-Host/Port/Prefix/Server` from every request (T80); the leader takes the container ranges out of the trusted proxies before they reach the nodes, and `SetClusterConfig` refuses a prefix of only container addresses (T79); `option forwardfor` then appends the connection's address, and `X-Real-IP` (removed from every request first) is set to `txn.client`, which `write_client_address` works out on every request: `src`, or from a trusted proxy the last `X-Forwarded-For` entry, stepping over trusted proxies up to 4 hops, unset when missing, invalid, or all trusted (fail closed); never on the internal frontend. Without certificates (`--tls=false`) `frontend http` writes the same body as `frontend https` (`X-Forwarded-Proto http`) instead of redirecting, sticky cookies lose `secure`, and app URLs start with `http://`. PROXY protocol (`--proxy-protocol`, container ranges taken out): `tcp-request connection expect-proxy layer4 if { src ... }` right after the bind of both public frontends. Client address rules: `ingress.ipAllow`/`ipDeny` (ranges with optional `name`/`description` for people, which never reach the proxy; external only, one of the two, ≤ 64; no zones, no IPv4-mapped, no /0) put `http-request deny deny_status 403 if { var(txn.ext) -m bool } ...` first in each backend and the wake backend (deny mode also refuses an unknown client). Sticky sessions: `ingress.sticky` (local-first off) renders `cookie <name> insert indirect nocache httponly secure attr "SameSite=Lax"` with a cookie name of `armada_` + 8 hex of the backend's SHA-256 and on every occupied slot `cookie r` + 12 hex of the replica name's SHA-256 (the same replica on every node); a slot taking another replica reloads. CORS: `ingress.cors` (listed origins or `*` alone, never `*` with credentials) answers preflights with `http-request return status 204` and adds `Access-Control-*` and `Vary: Origin`, in every backend of the app and its wake backend. All of these are in the configuration's signature, so a change reloads.
- Proxy certificates by reference (ADR 0004): agents announce `Hello.certificate_refs`; their assignments carry each certificate as name + SHA-256, and the agent (`with_certificates`) fetches missing or changed ones with `GetCertificates` (≤256 per call, only certificates the configuration serves), checks the digest, and caches them in memory. The agent dials with a 64 MiB receive limit.
- Proxy configuration per pass (`server/src/ingress.rs`, `proxy_config`): an address or container IP that replicas of two apps claim (`claimed_twice`, one of them stale) goes into neither backend, and each app records an `AddressConflict` condition, like the network endpoints for the firewall; hosts under the root domain belong to the app or labelled revision they name (`root_hosts`), a custom domain naming the app's own one is routed once (`app_hosts`), and a public host+path another backend holds is left out with a `RouteConflict` condition (T87) instead of failing the configuration; certificates are read from storage once and kept until obtained or renewed again; when building fails, the pass still pushes replicas with the last valid configuration and records one `ProxyNotUpdated` event; validation limits (100k backends, 1M rules, 100k certificates, 2 × the maximum replicas servers per backend for rollouts) only bound what a compromised control plane can make an agent render.
- HAProxy health checks: `default-server check inter 2s fastinter 1s fall 2 rise 2 observe layer4 error-limit 2 on-error fastinter`; servers on other nodes get `inter 15s`, so a node does not check every replica of the cluster every 2 s; failed real connections switch any server to 1 s checks.
- HAProxy's own statistics (`frontend metrics`, Prometheus exporter) bind only to `127.0.0.1:8404`: they name every space's apps, so neither the private network nor containers reach them.
- HAProxy (`agent/src/haproxy`: `config.rs` validation, `mod.rs` the driver, `api.rs` the Runtime API, `engine.rs` the system container; the renderer in `node/src/proxy`): structural changes (new app/domain/route) = re-render + `haproxy -c` + reload (SIGUSR2, then wait until `show info` names a new process, at most `RELOAD_WAIT` 10 s, so live changes after it reach the new process; a timeout makes the next apply reload again); deploy/scale/drain/certificates = Runtime API over a Unix socket (`set ssl cert` payloads without the empty lines issued bundles have between blocks; a live certificate update that still fails reloads HAProxy, which reads the new file). Do not use the Data Plane API. Files are written 0600 and atomically. Long-lived connections: `timeout tunnel 1h`, `hard-stop-after 1h`; `ingress.timeout` renders `timeout server` in the app's backend. A new agent takes over a running proxy with no reload when the configuration differs only in server lines (`live_config`, `same_structure`; slots from `show servers state`, the same certificate names). Local-first routing (ADR 0024): unless the app splits traffic, `be_<app>` is `balance leastconn` with each server weighing 11 on the node's private IP or in its container subnet and 10 otherwise, set through the Runtime API like an address; idle servers tie, so the backend's own `use-server` rule picks a local slot from `local.map` while `be_conn` is at most 1, for requests from the internal frontends only (`!{ fe_name http } !{ fe_name https }`): public requests arrive at one node often and would all stay on it at low load, so they balance over every replica. Nothing about local-first reloads the proxy or adds a frontend rule; every `http-request` rule is written before the `use_backend` rules. A rule that matches a whole host with no `ingress.allow` and no wake needs no rules of its own: it goes into `routes-<frontend>-<hash>.map` (0600, named after its content, `<space>/<host>` keys on the internal frontend so another space's caller finds no route), and `use_backend %[var(txn.route)]` picks its backend, so a request's cost does not grow with the apps of the cluster. The layout is keyed by HAProxy backend name; load totals keep growing across reloads (read just before a reload and carried over to the new process).
- Rollouts (ADR 0005): an app has an `active_revision` (serving) and a `target_revision` (rolling out). Agents decide readiness through probes (`agent/src/probe.rs`, `check.rs`), HTTP or a `command` run like `armada app exec` (output dropped, arguments never logged) (a container older than the agent stays out of reports until a first verdict; the implicit port check slows to about 10 seconds once ready); the server only puts `running` + `ready` replicas in the proxy, retires old replicas after the warm-up, and deletes them after the drain timeout (`drain` in the spec, default 10 s), counted from the later of when draining started and the leader's term start, and held up to `AWAY_HOLD` (1 min) more while a node is away (disconnected, not lost), except for apps with volumes (`finish_drain`). Never delete a replica that serves traffic without draining it. The agent applies the proxy before removing containers it no longer wants, reconnects every second (jittered) for 2 minutes after a session it had ends (`reconnect_wait`), gives up on a session the server does not answer within `SESSION_ANSWER` (10 s), and the gRPC channel's backoff is capped at 1 s.
- Removing an app: `RemoveApp` marks the app removing (audited; refused for jobs); the leader's `reconcile_removal` retires its replicas through the normal drain and deletes the app (revisions and secrets, in one transaction, only with no replicas left). Deploy refuses a name being removed. Volumes stay, so `armada volume delete` works with the app gone, and a space holding them cannot be deleted until then.
- Secrets (ADR 0006, ADR 0052; `store/src/secrets.rs`, `server/src/secret_api.rs`, `secrets/`): a secret belongs to a space and holds keys; it is named by an ID like an app's, and the secret with an app's ID is that app's own: `secrets/<ID>/<key>/<version>`, `secretseq/<ID>/<key>`, and the RPCs `SetSecret`/`ListSecrets`/`DeleteSecret` (their `app` field is the secret's ID, `name` the key; `DeleteSecret.whole` deletes every key), plus `ListSpaceSecrets`. A spec reference is `KEY` (the app's own secret) or `SECRET/KEY` (resolved within the app's space; another space is never reachable); keys are a secret name or a variable name. Revisions pin each reference as written, and Deploy records the app under `secretusers/<secret ID>/<app ID>` for every other secret it pins, which pruning, deletes, `ListSpaceSecrets`, `ListSecrets` used-by, `SetSecret` rollouts of every app whose target revision uses the key, and the bucket checks read. `RestartApp` deploys a new revision of the target spec with the latest versions even when nothing changed (refuses jobs, traffic splits, apps being removed; runs the stored-revision and bucket checks with the latest values first; audits `app.restart`, records `Restarted`). An app's secret stays while another app pins it. Deploying a spec that uses space secrets needs schema 15. Values are encrypted with envelope AES-256-GCM (master key `master.key`, the secret's ID and key as scope and name). The server decrypts only while building a node's assignment, and keeps the versions it opened in memory across passes (dropped once no pass uses them or the secret is deleted; never in etcd or logs); versions are never reused (`secretseq` keeps a deleted secret's last version), and done or draining replicas whose pinned version is gone get the reference only; the agent writes secret files only to its tmpfs secrets directory. Never log `ReplicaSpec`, `Assignment`, or `SetSecretRequest` (their `Debug` prints every field), and never put secret values in container labels or the spec hash.
- Armada's containers and resources are identified by `armada.*` labels and must be idempotent: an agent can restart at any time and adopt existing containers. The agent runs as `armada-agent.service` on every machine, servers included (`armada-server.service` wants it), and holds an exclusive `flock` on the data directory (`lock_data_dir`), so a second agent on a node is refused; the server takes no lock.
- armada-kv (ADR 0057, steps 1 and 2; `kv/`): Armada's own store, not used by the daemon yet. Members serving the subset of etcd's v3 API armada-store uses with etcd's messages (armada-proto generates etcd's servers too): KV Range/Put/DeleteRange/Txn/Compact, Watch, Lease Grant/Revoke/KeepAlive, Cluster MemberList/MemberAdd (learners only)/MemberPromote/MemberUpdate/MemberRemove, Maintenance Status/Snapshot; everything else `Unimplemented`, errors with etcd's codes and texts (`kv/src/error.rs`). `mvcc.rs`: one redb database (`<dir>/kv.db`, the directory 0700, one holder at a time) with tables `latest`, `history` (key, revision → version or tombstone), `events` (revision, n → change), `leases`, `lease_keys`, `meta` (format, revision, compacted, applied, member and cluster IDs); a new store is at revision 1. Every change is a `command::Command` (a protobuf message of etcd's requests; the lease ID and expiries decided before it is made), applied deterministically in one durable commit per batch of committed log entries (at most 256), each command at most one revision; transactions are checked as etcd checks them (4096 operations, duplicate keys in either branch, then the branch's lease and revision checks before any change) and read their own writes; reads (and transactions of ranges only) go to a read transaction without a commit, after a ReadIndex unless every range is serializable. Raft (step 2) is openraft 0.10 (one leader per term, pre-vote; no serde: `raft.rs` encodes entries, votes, memberships, and peer messages as hand-written protobuf messages): `log.rs` keeps the log (`raft_log`) and the vote, purged and committed IDs (`raft`) in the same redb file, each change one durable commit; `sm.rs` applies committed entries with `Store::apply_logged` (no quota check: the leader refuses commands that grow a full database before proposing, since file sizes differ per member) writing the last applied log ID and membership in the same commit, and its snapshots are `snapshot.rs`'s format plus that metadata (installing one replaces the key space in one commit and keeps the member's and cluster's IDs). The member ID is the Raft node ID; a member's node in the membership holds its name and peer and client URLs (a member MemberAdd added publishes its name and client URLs once started, as etcd's do). `node.rs`: `Start::New` bootstraps a one-voter cluster, `Start::Join(peer URLs)` asks those members for the member list and takes the ID of the member with its own peer URL and the cluster ID; a member that has Raft state ignores both. Any member takes any request: one that does not lead forwards commands, ReadIndex, keep-alives, and membership changes to the leader over `peer.rs` (`armadakv.Peer`: unary `Call` and client-streaming `Snapshot`, each request naming the cluster and the member it is for; a forwarded command whose transport fails is answered with the error, never retried) and answers the client itself; linearizable reads wait until the member applied the leader's ReadIndex. The lease clock (every 250 ms, TTLs raised to 2 s) and the compaction run on the leader only, which gives every lease its whole TTL again when it becomes the leader and confirms it leads (ReadIndex) before renewing a keep-alive; an expiry decided by a member that no longer leads is never forwarded. `Connector` opens peer connections (`UnixConnector` for `unix://` peer URLs; mutual TLS comes with step 3), `serve_peer_unix`/`PeerDispatch` serve the peer service. Status reports the leader, raft index and term, applied index, and learner state; compaction keeps an hour of history (`Options.retention`), each key keeping its newest version at or below the compacted revision. `snapshot.rs`: magic, a header (format, revision, counts), the leases and current keys, a SHA-256 at the end; `Store::restore` writes a new database compacted at the snapshot's revision with new IDs. `service.rs` serves the five services behind one `Dispatch` (1.5 MiB requests, `etcdserver: request is too large`), `serve_unix` on a 0600 socket bound through its directory's descriptor. Step 3: TLS listeners on the cluster CA, `armadad kv` and its unit.
- State lives in etcd (ADR 0009), run by `armada-etcd.service` from the pack's pinned etcd (ADR 0055; `armadad etcd`, `daemon/src/commands/etcd.rs`: works the member out (name, `<dir>/data`, client and peer URLs, initial cluster and state, token, TLS files) and writes `etcd/etcd.yaml` 0600 (TLS 1.3, client certificates on both listeners with `allowed-cn`, no gateway or metrics listener, `max-txn-ops` 4096, periodic compaction 1h), refuses while another process holds the member's database (`hold_member`), then execs etcd; it installs the pack first under `.install.lock`, so it and the agent never install at once). `armadad server` connects to it (up to a minute; takes its ID and learner state from it and updates the peer URL). The store (`store/src`): JSON records under `/armada/`, optimistic serializable transactions (`tx.rs`; the body may run more than once, so no side effects outside it), over its own etcd client (`client.rs`: TLS 1.3 with the member certificate read on every handshake). etcd accepts only TLS 1.3 client certificates with the shared `etcd:member` identity (the Armada API refuses it) and listens on the server's private IP, never publicly; the member certificate names every private address of the machine (do not skip etcd's client SAN check). Transactions delete many keys by range (one operation each; no write into a deleted range in the same transaction): app and job deletion and the audit trim; etcd allows 4096 operations per transaction. A transaction reads one app's replicas by key prefix (replica IDs start with `<app>-`, and the record's app still decides, since `web-` also holds `web-api`'s). Domain claims and pruning still read every live spec. A reconcile pass logs an app it cannot reconcile, records `ReconcileFailed` once (a condition), and goes on with the others; only losing the leadership or a cancelled context end the pass. A node's status write is skipped when only a last-seen time less than 30 s newer changed, so agent reports do not move the commit key under every other transaction. Incompatible record changes bump `SCHEMA` (15) with a migration (`migrate.rs`); a binary refuses a newer schema. Reads of many revisions go through `get_many` (read-only transactions of `READ_BATCH` gets at the snapshot revision). A new file in the data directory must be added to the backup's layout (a test checks it).
- Control plane topology (ADR 0010): one server is supported, three are recommended. Servers elect a leader through etcd (`store/src/election.rs`, `Leadership::campaign` on `/armada-leader/`); only the leader serves the API/join listener and runs reconcilers and the certificate manager, each term with a fresh server and a store fenced on the election key (`server/src/lifecycle.rs`). Servers join with a single-use server token (`server join-token`, `armadad server join`), which hands over the CA and master keys; new members start as etcd learners and are promoted by the leader. Agents and the CLI hold every server address and dial them in order. The leader puts the API addresses of its last pass in the `armada-servers` header of every AdminService answer; the client writes a different set back to its config once per run (silently; a shared config only as root; a config with a loopback address no server has, an SSH tunnel, is kept). An agent run as root from the default data directory writes its server list to `/etc/armada/servers` (0644, its directory given o+x explicitly since the units' umask is 0077, at start and on every change), and the client appends its addresses the config lacks (root-owned, not group/other-writable, ≤64 KiB, private addresses only). `armadad server join` run as root writes `/etc/armada/admin.config` like init (a user certificate for `--user-name`/the sudo user signed with the received CA; an existing file kept; failure only warns) and adds the sudo user to the group.
- The replays (`make replays`): recorded behaviour, goldens nothing writes again, replayed against the code: the store's methods on a pinned etcd member (`store/tests/replay.rs`), the control plane's scenarios driven through AgentService, AdminService, and JoinService with fake agents, volume sessions, an S3 stand-in, alert stand-ins, and scraped metrics (`server/tests/scenarios.rs`, `server/tests/replay`), the agent's scenarios against a fake runtime, proxy, network, resolver, certificate source, and armada-node, with a control plane and a log endpoint in the test (`agent/tests/scenarios.rs`, `agent/tests/replay`), the client's and the daemon's commands (`client/tests/parity`, `daemon/tests/parity`, doctor cases on a machine of the case's own under `ARMADA_DAEMON_TEST_HOST_ROOT`). The pki, secrets, spec, proto, and renderer cases replay in `make test` (`tests/parity.rs` and the like). The test programs (`armada-store-parity`, `armada-server-parity`, `armada-agent-parity`, `armada-agent-fake-node`) stay behind the `parity` feature and the hooks behind `test-hooks`, never in a release (`armada-spec-check` is never packed).

## Code conventions

- Everything is in **English**: code, identifiers, comments, commit messages, error messages, and all documentation (open source project for a global audience).
- Licenses (mandatory): Armada is Apache-2.0 and must stay free for commercial use. `armada-log` (`logger/`), `armada-shim`, and `armada-dns` use the Rust standard library only (`armada-pack`'s notices tests), and the notices name the libraries they link statically (Rust std, musl); the Cargo workspace at the root (ADR 0055: `armada-node` in `node/`, ADR 0054, `armada-proto` in `proto/`, and `armada-fsutil`, `armada-pki`, `armada-secrets`, `armada-spec`, `armada-store`, `armada-kv` (ADR 0057), `armada-server`, `armada-client`, `armada-agent`, `armada-daemon`, `armada-pack` (the pack's build tool, never shipped) in `fsutil/`, `pki/`, `secrets/`, `spec/`, `store/`, `kv/`, `server/`, `client/`, `agent/`, `daemon/`, `pack/`) may use crates only under Apache-2.0, MIT, BSD-2-Clause, BSD-3-Clause, ISC, MPL-2.0, CC0-1.0, or Unicode-3.0 (Unicode data), checked from the root `Cargo.lock` in CI (`deny.toml`) and listed in `THIRD_PARTY_NOTICES.md` (`armada-pack`'s notices tests), their license files in release archives (`scripts/rust-licenses.sh`, `third_party/licenses/rust/` for a crate published without one); `proto/gen` (the generator of `make proto`, never distributed) keeps its own lock outside the workspace; never GPL, AGPL, SSPL, BUSL, or anything that limits commercial use in Armada's own programs or anything they link, and no copied code under such licenses. One exception (ADR 0056): a program under the GPL may be in the runtime pack when Armada's programs only run it as a separate process (never link it or any of its code) and the release carries its complete corresponding source and its license, pinned in `pack/lock.json` (`license`, `sources`: crun's release tarball and the build files of its static programs, each by SHA-256; `armada-pack sources`, `make runtime-sources`); `armada-pack`'s tests refuse a GPL pin without them, and AGPL, SSPL, and BUSL pins at all. Commercial use and running Armada as a service stay unrestricted. Do not change MPL-2.0 files of a dependency. Changing an embedded runtime program (`pack/lock.json`) updates `THIRD_PARTY_NOTICES.md` in the same change (`cargo test -p armada-pack`); its static libraries (glibc, libseccomp, libgcc, and crun's libcap, json-c, libcriu, protobuf-c) are listed there with their licenses and source, and pinned in `pack/lock.json` `linked` and `libraries` (each library's source tarball, patches, and build files by SHA-256, or `noSource` naming the license exception that waives it: libgcc's GCC Runtime Library Exception; tested). Release archives carry `LICENSE`, `THIRD_PARTY_NOTICES.md`, `third_party/licenses/`, `licenses/rust/`, and (full Linux archives) `licenses/runtime/`, the license files of the Go modules the pack's etcd programs link and crun's license texts (`crun@<version>/`), and `licenses/runtime/SOURCES.txt`, which names the release asset `armada_<version>_runtime-sources.tar.gz` (one for every architecture, in `checksums.txt`): crun's complete corresponding source and the libraries' sources under `source/runtime/`. The archives carry no source. Images Armada pulls at run time (HAProxy, GPL-2.0) run as separate containers and are never linked or bundled.
- Commit subjects follow Conventional Commits, `type(scope)!: description`, because the release notes are grouped by type (`.goreleaser.yaml`) and CI rejects other subjects (`scripts/check-commits.sh`). Types: `feat`, `fix`, `security`, `perf`, `docs`, `deps`, then `refactor`, `test`, `ci`, `build`, `chore`, `style`, `revert`; `!` marks a breaking change. Write the description for the people reading the release notes. `main` only changes through pull requests that pass every CI job (repository ruleset; see docs/releasing.md).
- Idiomatic Rust (edition 2024), `cargo fmt` and `clippy -D warnings` clean (`make lint`, with and without the test features); no `unsafe` beyond the system calls that need it. Error texts, outputs, and file formats are behaviour: the replays compare them with the recorded behaviour, so change them only on purpose, and change the recording with them.
- Code lives in the workspace's crates, one directory per crate at the root (`publish = false`: Armada has no public Rust API), and in `logger/`, `shim/`, and `dns/`; the protocol is `api/armada/v1/armada.proto`, generated into `proto/src/gen` by `make proto`. Test programs and hooks stay behind the `parity` and `test-hooks` features, never in a release.
- Every runnable command of both binaries has two to four examples a person can copy (`Node::example`, `client/src/cli`); help prints usage, examples, description, flags.
- YAML specs are parsed strictly (unknown field = error). Features whose types exist but are not implemented yet must be rejected with a clear message, never silently ignored.
- Tests live next to the code (`#[cfg(test)]` modules) or in each crate's `tests/`. Reconciler logic is tested with fakes, not a real runtime. HAProxy renderer changes come with their recorded cases (`node/tests/testdata/render.jsonl.gz`, by hand) and `make haproxy-check`.
- Development and CI always use ACME staging or Pebble, never the Let's Encrypt production endpoint.

## Keeping documents current (mandatory)

Every change updates, in the same commit or pull request, every document it makes stale. A change is not done until its documents are; do not leave it for a follow-up. Before committing, check at least:

- `README.md`: the short feature table and the document links; `docs/features.md` (full feature list) and `docs/tested-environments.md`.
- `docs/cli/`: run `make docs` whenever a command, flag, or help text changes (generated; never edit by hand).
- `docs/guides/`: the guides that use the changed feature (task recipes; every command and spec in them must stay valid), `docs/concepts.md` for changes to the core ideas, and `docs/README.md` (the documentation home) for new pages.
- `CLAUDE.md`: Status, Commands, Architecture in brief, and these conventions.
- `docs/compatibility.md`: what is stable and what is deprecated; a change to anything it calls stable needs a deprecation there first.
- `docs/`: quickstart, operations guide, spec reference, `threat-model.md` for anything that changes the attack surface or a mitigation, and `docs/adr/` for design decisions (a new ADR, or an update to the one the change supersedes, plus the index in `docs/adr/README.md`).
- CLI help text and error messages that describe the changed behaviour.

## Security rules (mandatory)

This is infrastructure software that holds root on every node. Treat these rules as merge requirements, not suggestions:

1. **Never weaken mTLS** (no certificate verifier that accepts anything, rustls' `dangerous()` included, no `--insecure` flag, no plaintext fallback), including for development or tests.
2. **User input into the HAProxy configuration** (domains, paths, app names) must pass whitelist validation in the spec crate (`spec/`) and be validated again before rendering (`agent/src/haproxy/config.rs`) and in the renderer (`node/src/proxy`). Never interpolate user strings into templates without validation, and never turn them into regular expressions.
3. **Secrets:** never print plaintext to logs, errors, CLI output, or the audit log. Secret types must redact themselves in `Debug` and `Display`. Never accept secret values as CLI arguments (they end up in shell history); read them from stdin or a file.
4. **Bind interfaces:** agent/server gRPC, internal DNS, HAProxy stats, and container ports bind only to private IPs. Only HAProxy on ports 80/443 faces the public; in a mesh cluster (ADR 0049) also the WireGuard port, and the leader's join listener only while a join token is open (T90); in a cluster with more than one site (ADR 0050) also the WireGuard port, and the leader's join listener on its endpoint only while a token for another site is open. Never bind internal services to `0.0.0.0`.
5. **Sensitive files** (CA key, master key, TLS private keys, `~/.armada/config`, state DB) are created with `0600`/`0700` permissions. Check permissions when reading them.
6. **Cryptography:** use ring (and rustls, rcgen, x509-parser on it) and ring's `SystemRandom`. Never invent cryptographic schemes. Compare tokens in constant time (`pki/src/join.rs`, `constant_time_eq`). Store join tokens only as hashes.
7. **Secure container defaults:** `no-new-privileges`, no `--privileged`, no host network, no container runtime socket mount, memory/PID limits. Any relaxation must be explicit in the spec.
8. **System images** (HAProxy) are pinned by digest, not by tag.
9. **Authorization** is based on the identity in the client certificate: an agent may only access agent RPCs and data for its own node.
10. Changes touching `pki/`, `secrets/`, the certificates' code (`server/src/certs.rs`, `server/src/acme`), the proxy renderer, or API auth must come with tests for negative cases (malicious input, wrong certificates, expired tokens) and, where relevant, an update to `docs/threat-model.md`.

If a request conflicts with these rules, explain the risk and offer a safe alternative before doing the work.
