# CLAUDE.md

Guidance for Claude Code when working in this repository.

## About the project

Armada is a multi-machine container platform (cloud instances, VMs, or bare metal; do not describe it as VPS-specific). Docs describe Armada on its own terms: do not compare it with or name other products unless a component or protocol really needs naming. Two Go binaries (ADR 0027): `armadad` runs on every machine as root, as `armadad server` (control plane) and `armadad agent` (runs containers through Armada's embedded containerd, ADR 0011), plus the machine commands (`init`, `join`, `doctor`, `backup`, `restore`, `runtime`); `armada` is the client that only talks to the API (no root, Linux and macOS). Ingress uses HAProxy as a system container managed by Armada.

- **Architecture decisions:** `docs/adr/`. **Threat model:** `docs/threat-model.md`

When the design changes, add or update an ADR in the same change. Never let code and documents contradict each other (see "Keeping documents current" below).

## Status

Phases 0–6 are done and tested end to end in local lab VMs (Pebble ACME) and in the cloud: a single server on Oracle Cloud (Oracle Linux 9, SELinux enforcing, Let's Encrypt staging, HTTP-01 and Cloudflare DNS-01 wildcard) three control plane servers on depa.id (leader stop and SIGKILL under load, rolling update through the new leader, all machines rebooted at once), a mixed cluster of those servers (amd64) with the Oracle machine (arm64) as a node, and two depa.id machines on the `wireguard` network mode with the kernel device. Phase 7 (hardening, documentation, release) is in progress: security review fixes, `armadad doctor`, signed release pipeline (GoReleaser + cosign + SBOM + provenance), `install.sh`, `armadad backup`/`restore`, self-healing (ADR 0008), the embedded etcd state store (ADR 0009), the HA control plane (ADR 0010), the embedded container runtime (ADR 0011), quickstart, spec reference and operations guide are done. Roadmap stage 1 (stable for others) is done: rolling upgrades with gated state migrations (ADR 0012), SELinux confinement of containers, replica rebalancing (ADR 0013), the cloud end-to-end test (`test/e2e`), and placement (ADR 0014: node labels, restricted nodes, `placement.require`, image platforms, CPU and memory reservations, `spreadBy`). Armada runs on Linux only, on the embedded runtime. Stage 2 (day-to-day operations) is done: `armada app exec` (ADR 0015), `armada app top` (ADR 0016), the metrics endpoint (ADR 0017), and event history (ADR 0018). Stage 3 is done: jobs and cron (ADR 0019), autoscaling (ADR 0020), scale to zero (ADR 0021), and traffic splitting (ADR 0022). Stage 4 is done: persistent volumes (ADR 0023). Local-first routing in HAProxy (ADR 0024) is done, the first step of the cluster network work before the alpha; the network benchmark (`test/bench`) and the cluster network design (ADR 0025) followed. ADR 0025 is being implemented: nodes get their own container subnet (stage 1a) and route them over a VXLAN tunnel with MTU, firewall, and doctor checks (stage 1b, the `plain` mode), with an encrypted `wireguard` mode and node keys (stage 1c), and replicas publish no ports (stage 2); stage 3 is designed together with projects (ADR 0026). Projects, network isolation (the nftables firewall between apps and projects, isolation from the platform, per-project DNS, the project check in HAProxy's internal frontend, and `ingress.allow`), the log rate limit, and usage per project are done. Stages 1–4 are in the first tagged release, `v0.1.0-alpha.1`. Since then the client and the daemon are separate binaries (ADR 0027), and each person has a certificate of their own that can be removed (ADR 0028), with roles for users and services (ADR 0033); specs take variables and variables from secrets (ADR 0029); machines find and install newer releases themselves (ADR 0030); and the client is `armada <noun> <verb>`, with apps and jobs created and updated from flags or files and exported as specs (ADR 0032); and apps also scale on the length of their queue and on schedules (ADR 0034); and replicas run init containers and sidecars beside the app's container (ADR 0038); and apps take plain TCP from their project inside the cluster (ADR 0039). Do not build features outside the agreed scope unless asked.

Module path: `github.com/ryanbekhen/armada`. The toolchain is pinned with `toolchain` in `go.mod` (a patch release with no govulncheck findings); golangci-lint must be built with the same toolchain.

## Architecture in brief

- **Desired state + reconciliation**: the CLI only writes desired state to the server; reconcilers on the server and agents converge actual state. Every operation goes through this path; never add a "just run the container" path from the CLI.
- Agents open the gRPC (mTLS) connection to the server; the server sends assignments over a bidirectional stream.
- Nodes (ADR 0003): joining goes through a separate join listener (server-only TLS, serves only `JoinService`, rate limited); the main API is always strict mTLS. The joining node pins the CA by hash without `InsecureSkipVerify`. Node certificates last 30 days, are renewed by the agent, and are only accepted while their serial is recorded in `node_certs` (removing a node revokes them). Each server renews its own server and etcd member certificates (`certRenewer`: at start before loading, then every 12h, `pki.RenewDue` = last third or expired) with `CA.Reissue` (same key, one file written atomically); `pki.ServerCert` serves the current one on every handshake (API, join, metrics), and etcd and `clientTLS` read the member files per handshake. Before the embedded agent starts, `certRenewer.renewNode` re-signs the machine's expired node certificate (recorded with `RecordNodeCert` first; a removed node is refused), otherwise the agent, and with it the server, could not start. Admin certificates: `armada admin renew` (`RenewAdminCertificate`, caller's own name, audited) or `armadad admin renew` with the CA on disk; doctor's `certificates` check warns and fails on expiry. Cordoned nodes get no new replicas and are evacuated without dropping below the desired serving count. Unevenly spread apps are rebalanced one replica at a time across the cluster through the same path (ADR 0013). Placement (ADR 0014): admin-only node labels (CLI or join token; `armada.os`/`armada.arch` reported by the agent, `armada.` reserved), restricted nodes, `placement.require`, and `placement.spreadBy` (soft: even over a label's values, then nodes; yields to capacity; only labelled nodes; rebalancing compares values first, then nodes within a value); every scheduling path (scale, rollout, self-healing, evacuation, rebalancing) only picks nodes from `eligible()`, and replicas on nodes that stop being eligible move like cordoned ones. Image platforms are learned from agents after a pull (or from the registry when the image has no variant for the node; `runtime.PlatformError`), kept once per revision like the digest, and restrict `eligible()`; the control plane never contacts registries. Replicas reserve CPU (`resources.cpu`, default 100m, also the limit when set) and memory with no overcommit; `allocatable()` subtracts what Armada keeps (100m CPU and 128Mi per node, 100m more on servers) before `pickNode`, and capacity only fits and breaks ties, never outranks the replica count (T28). `pickNode` also skips a node with its own subnet at `maxSubnetReplicas` (250, `replicasFull`;
finished job attempts hold no address). A replica that has kept failing to start for a minute, outside a rollout, is replaced on another node that fits (`moveFailed`, one per app at a time). A pass works out once what each app needs to know about all the replicas (`reconcileRun.view`, `replicaView`: replicas per app, `placedUse` per node), again only after a change, so its cost does not grow with apps times replicas. `ReplicaSpec.cpu_reserve_millis` sets the container's CPU weight and stays out of the agent's spec hash.
- Internal ingress (ADR 0007): `<app>.internal` is served by a HAProxy `frontend internal` bound to the container bridge gateway (`armada0`) (never the private IP: NAT and load balancers make that reachable from the internet) and resolved by the agent's DNS server (`internal/dnsserver`) on the same address, which answers only the bridge subnet. Internal and public rules never mix; the `.internal` zone is reserved.
- Container runtime (ADR 0011): the only runtime is Armada's own containerd, run from binaries pinned in `internal/runtime/embedded/lock.go` and embedded in release builds (build tag `bundle`); `armada-runtime.service` runs `armadad runtime`, which extracts and verifies the pack and execs containerd (own root, socket `/run/armada/containerd/containerd.sock`, namespace `armada`, config format 4 with `imports = []`, no CRI/NRI/TCP/debug/metrics, restart monitor disabled). `internal/runtime/containerd` builds the OCI spec itself (shared checks in `runtime.CheckContainerSpec`), uses CNI (`armada0` with a fixed MAC from `bridgeMAC`, host-local IPAM on tmpfs with a default route, portmap on the private IP, firewall), unique container IDs per creation (`<name>-<hex>`), and logs through `armadad runtime-log` (`embedded.WriteLogs`: rotation at `runtime.LogMaxSize`×`LogMaxFiles`, and a token bucket of `LogRate` 1 MiB/s with `LogBurst` 4 MiB per container; excess is dropped, never blocked, and counted in one stderr line when output fits again or at close). `agent.json` records `"runtime": "embedded"` (any other value is refused: remove and rejoin the node).
- Admin config (ADR 0027): `armadad init` writes `clientconfig.SystemPath` (`/etc/armada/admin.config`, root:`armada` 0640 via `SaveShared`, `/etc/armada` gets o+x only); `clientconfig.DefaultPath` = `$ARMADA_CONFIG`, else `~/.armada/config` if it exists, else the system path; `Load` accepts group read only for root-owned 0640 group `armada` (`sharedOK`); `SaveFile` keeps a shared file shared; the installer creates the group. Run through sudo, init also writes `~/.armada/config` of `SUDO_USER` (`SaveOwn`: `os.Root` on the home, `O_EXCL`, chowned; failure only warns) and names the first user (cluster-admin) after them; an unreadable shared file says whether the account is outside the group or joined after the session started (`groupAdvice`).
- Access control (ADR 0033): principals are users (`pki.KindUser`, one year, `SignUserCSR`) and services (`pki.KindService`, 90 days, `SignServiceCSR`); `Identity.Principal()` reads the old kinds `admin`/`automation` as user/service. `store.Principal` records under `users/` and `services/` (schema 9, `migrateAccess` moves `admins/` and `automation/` without changing rights) hold `Roles []Grant` (role + project, "" = cluster; `CheckGrant`: `cluster-admin`/`project-creator` cluster only, `deployer`/`admin` one project and never `default`, `viewer` either) and allowed node `Labels`. Users: `Since` (certificates with an earlier NotBefore refused), deleted = tombstone; `UserAccess` gives a name with no record cluster-admin (only the CA signs those: init before records, `armadad user renew`), `KnowUser` records such a name with cluster-admin (init, renew). Services: recorded serials (`RecordServiceCert`, keep = renewal), `ServiceAccess`. `authorizePrincipal` (`internal/server/auth.go`) reads roles on every call: cluster-admin calls every `AdminService` method; others only methods in `methodNeeds` (`access.go`: `needView`/`needDeploy`/`needAdmin` project levels, `needCreateProjects`, `needSelf`; anything missing is cluster-admin only, tested over the whole service descriptor) that a role `reaches`; handlers check projects through `accessFrom(ctx)` (`app`, `project`, `sees` against the method's level; `creates`; `placement` against the labels; `admin()` = cluster-admin or `internalContext`). RPCs (`rbac.go`, cluster-admin only): `CreateUser`, `IssueUserCertificate`, `CreateService`, `IssueServiceCertificate`, `ListPrincipals`, `UpdatePrincipal`, `DeletePrincipal`, `CreateAssignment`, `DeleteAssignment`, `ListRoles`; `RenewOwnCertificate` for any principal. Nobody deletes themselves or drops their own cluster-admin. `CreateProject(.., by)` makes a project-creator `admin` of the new project in the same transaction; `DeleteProject` takes every role in it back (`forgetProject`). Non-cluster-admins get no nodes and no cluster events.
- Platforms: Armada runs on Linux only (linux/amd64 and linux/arm64 releases); only the `armada` client also builds for macOS (darwin archives, client-only `install.sh`). Binaries (ADR 0027): `internal/daemon` (`cmd/armadad`) holds every command that runs on a machine; `internal/cli` (`cmd/armada`) only talks to the API and never imports `internal/daemon` or what a machine needs (`TestClientDependencies`); the daemon reuses `cli.Run`, `cli.RPCError`, `cli.ReadSecretValue`, `cli.NewVersionCommand`. Tests that run a server in process and drive client commands live in `internal/daemon` (`execute` sends each command to the binary that has it). Removed `Hello` fields (`runtime`, `min_memory_bytes`) are reserved in the proto.
- Command line (ADR 0032): `armada <noun> <verb>`, the root holds only nouns and `version`; no old names or aliases beyond `ls`/`rm` and plural nouns (`TestCommandAliases`). `app create`/`update` and `job create`/`update` (`internal/cli/appspec.go`: `specFlags`, `runCreate`, `runUpdate`) build a `spec.App` from flags (or read `--file`, with `--vars`/`--var`), validate it with `spec.ParseIn` after `Export`, and send `DeployRequest` with `must_create`, or `must_exist` + `base_revision` (the revision `GetAppSpec` returned; flag updates only), so a change in between is refused; `--diff` prints a line diff (`diff.go`) of the exported specs and deploys nothing. `app show`/`job show -o yaml` print `GetAppSpec` as is. `app list` follows `ListApps`' `next_page_token`; `cluster status` is `ClusterStatus`. `Status` with an app (`app show`, rollout waits every second; `appStatus`) returns that app and no nodes, reading its own replicas (`ReplicaFilter{App}`), the node records, and only its own domains (`appURLSource`); every replica and the servers (`allocatable`) only when `placementNeedsCluster` says its placement message compares with them. Other read paths stay in a few batches whatever the cluster's size: `ListVolumes` (`mountedVolumesOf`: `store.GetApps`, then `GetRevisions` for targets), `ListJobs` (runs grouped by job), `ListProjects` (counts from `store.ListAppIDs`, keys only). The project: `--project`, else `ARMADA_PROJECT`, else `clientconfig.Config.Project` (`project use`, checked with `ListProjects`), else default (`globals.resolveProject` in the root's `PersistentPreRunE`); `-A` spans projects in lists. Output: lists print a table only, actions one line of what happened, `-o json` (protojson) on everything that prints data (`outputFlag`); `dialAdmin` is a variable so tests drive commands against a fake client.
- Starting replicas (ADR 0011): `Agent.Reconcile` decides without starting anything, then `startPending` starts at most `maxConcurrentStarts` replicas at once, each image pulled once per credentials (`pullOnce`, for that set of starts only). Every `startReportInterval` it applies the firewall for finished starts, applies proxy changes, and sends a report of the rest; a replica still starting is left out. `Driver.Run` holds its lock only for replicas that publish a port. Every `ImagePrune` (10m) the reconcile loop calls `Agent.PruneImages` under `reconcileMu` (after the first assignment): `runtime.ImagePruner` removes images no container in the namespace uses, not named (reference or digest) by the assignment or `digests`, and not pulled within `imagePruneGrace` (1h); the last delete is synchronous so containerd frees content.
- Exec (ADR 0015): `armada app exec` opens `AdminService.Exec`; the server picks the replica (or a running, ready one of the serving revision), audits the command's name (never its arguments), and offers an `ExecRequest` over the node's Connect stream; the agent checks the replica is its own, then opens `AgentService.ExecSession`, which the server accepts once and only from that node (`execRouter`, like `logRouter`). Runtimes implement the optional `runtime.Execer` (`CanExec`); the process copies the container's own process spec, so it keeps every security setting. `runtime.CheckExecCommand` bounds commands (64 args, 4096 bytes, no NUL) on every hop; 32 KiB per message, 8 sessions per agent, 30 minutes idle. Never log or audit exec arguments.
- Usage (ADR 0016): agents sample running replica containers every 10 seconds through the optional `runtime.StatsReader` (embedded: containerd task cgroup v2 metrics, memory without inactive file pages) and send a `UsageReport` (CPU as millicores over the interval) on the Connect stream, apart from `ReplicaReport`. The leader keeps the latest sample per node in memory only (`usageStore`, never etcd; 35 seconds, bounded values, at most 1024 replicas, dropped on disconnect); `AdminService.Top` counts a replica's usage only from the node it is assigned to. Memory kills: `Stats.OOMKills` (cgroup `oom_kill`, readable until the container is removed) makes `crashed` say "out of memory", and a rise while the container runs reaches the leader as `ReplicaUsage.oom_kills` and becomes an `OutOfMemory` event (`usageStore.outOfMemory`: own node only, at most 8 per report). Connection tracking (ADR 0025, `internal/conntrack`): with each sample the agent raises `nf_conntrack_max` to `Target` (262144, or memory ÷ 4 KiB on small machines; never lowers; `Config.Conntrack`) and reports `UsageReport.conntrack_entries`/`conntrack_max`; `NodeTop` carries them to `armada_node_conntrack_*`, and doctor warns at 80%.
- Lost network: the same sample reads `/proc/PID/net/dev`; a replica's container with no `eth0` over two samples (`Stats.NetworkLost`, `restartLostNetwork`) is recreated like one a failed liveness probe restarts. Job attempts are not.
- Metrics (ADR 0017): only the leader serves `GET /metrics` on `--metrics-listen` (private address, TLS 1.3 with the API's server certificate, client certificate required; `metricsAuth` lets only `metrics:` identities and principals with cluster-admin through). `pki.KindMetrics` is refused by every RPC and by etcd; `AdminService.IssueMetricsCertificate` signs a caller's CSR (`pki.SignMetricsCSR`: identity from the CA, one year, audited). The collector (`clusterCollector`) gathers from `Status`, `Top`, `listJobs` (jobs with their runs by job, one read), and `ListVolumes` at most once per `Config.MetricsCache` (default `metricsCacheFor`, 10s): scrapes within it get the last set, scrapes during a gathering wait for it (`gathering`), a failed gathering is not kept; label values are only store-validated names (app, replica, revision, node, server), replica IPs (`addressIP` of the validated address), fixed words Armada picks (rollout state, `replicaStateLabel`, `restartReason`), and, as the one spec-written value, the image of `armada_revision_info` (revisions that serve, roll out, or have replicas, read in one `GetRevisions` batch), never domains, env values, or agent messages. `armada_app_autoscale_last_scale_timestamp_seconds` comes from `store.App.ScaledAt`, which `AutoscaleReplicas` sets (`Autoscale.last_scaled_at`, `armada app show` "Last scaled"). Restarts: `UpdateReplicaStatus` counts a new container ID of an app replica (`Replica.Restarts`, `LastRestartAt`) and takes `LastRestart` from the agent's `store.RestartNote` prefix, which may arrive with a later report; `CreatedAt` is set by `CreateReplica`.
- Events (ADR 0018): only the leader records them (`Server.record`, `internal/server/events.go`), from transitions it already sees (reconciler, agent replica reports via `replicaEvent`, API calls, ACME callbacks); the agent protocol is unchanged. `store.PutEvent` writes under `events/` with an hourly etcd lease (24h TTL), outside the state transaction but fenced; at least 2000 and 20 per app and node kept, at most 50,000 (`Server.eventKeep`, cluster size from the last pass; `TrimEvents` deletes the oldest with one range delete). Repeats of kind+object+reason within 10 minutes update one event (count); lasting conditions use `Server.condition` (recorded once until cleared). Messages are cut to 512 bytes with control characters replaced, and the CLI replaces them again. Recording never fails the caller. `AdminService.Events` (admin only) lists and, with `follow`, streams; slow followers are dropped. `armada_events_total{kind,reason}` on the metrics endpoint. Never put env values, secrets, or exec arguments in events.
- Jobs (ADR 0019): `kind: job` specs are stored as apps (revisions pin secrets) but with no rollouts (deploy makes the revision active at once; `scale`/`rollback` refuse; `Status` leaves them out). Runs are `store.JobRun` records under `runs/<job>/<seq>`; each attempt is a replica with `Run` set, built into the assignment with `ReplicaSpec.job` (`JobAttempt`; `done` is outside the agent's spec hash). The leader's `reconcileJobs` (`internal/server/jobs.go`) schedules (latest due fire; `LastScheduled` written with the run so a fire runs once; >1h late is `Missed`; `concurrency` forbid/replace), places attempts only on `eligible()` nodes whose agent announced `Hello.jobs`, ends attempts on exit/start failure/lost node/timeout, retries with backoff, and prunes to `history` (containers kept 24h, done replicas reserve nothing). The agent (`internal/agent/job.go`) never restarts an attempt, reports `finished`+`exit_code`, and stops but keeps a done attempt's container, with its address released (`runtime.NetworkReleaser`). Schema 3 gates jobs to servers that know them (schema 4 does the same for traffic, schema 5 for volumes, schema 6 for the cluster network, schema 7 for projects, schema 8 for administrators). Runs are at least once.
- Autoscaling (ADR 0020): `scale.rules` (`http` concurrent, `cpu`/`memory` utilization of the reservation, and `queue`/`schedule` from ADR 0034). - Rollouts (ADR 0005): an app has an `active_revision` (serving) and a `target_revision` (rolling out). Agents decide readiness through probes, HTTP or a `command` run like `armada app exec` (`checkCommand`; output dropped, arguments never logged) (a container older than the agent stays out of reports until a first verdict, `awaitsVerdict`; the implicit port check slows to about 10 seconds once ready, `implicitPeriod`); the server only puts `running` + `ready` replicas in the proxy, retires old replicas after the warm-up, and deletes them after the drain timeout (`drain` in the spec, default 10s, `drainFor`). Never delete a replica that serves traffic without draining it.
- Removing an app: `RemoveApp` sets `appRec.Removing` (`MarkAppRemoving`, audited; refused for jobs); the leader's `reconcileRemoval` retires its replicas through the normal drain and calls `DeleteApp` (revisions and secrets, in one transaction, only with no replicas left). Deploy refuses a name being removed. Volumes stay, so `armada volume delete` works with the app gone, and a project holding them cannot be deleted until then.
- Secrets (ADR 0006): per app, versioned, encrypted with `internal/secrets` (envelope AES-256-GCM, master key `master.key`). Revisions pin secret versions. The server decrypts only while building a node's assignment, and keeps the versions it opened in memory across passes (`openedSecrets`, dropped once no pass uses them; never in etcd or logs); the agent writes secret files only to its tmpfs secrets directory. Never log `ReplicaSpec`, `Assignment`, or `SetSecretRequest` (protobuf-go ignores `debug_redact`), and never put secret values in container labels or the spec hash.
- Armada's containers and resources are identified by `armada.*` labels and must be idempotent: an agent can restart at any time and adopt existing containers. `armada-server.service` already runs the node's agent; `runAgent` holds an exclusive `flock` on the data directory (`lockDataDir`), so a second agent on a node is refused.
- State lives in etcd embedded in `armadad server` (ADR 0009; `internal/etcd` runs the member, `store.Etcd` implements `store.Store`): JSON records under `/armada/`, optimistic serializable transactions (`Etcd.tx`; the callback may run more than once, so no side effects outside it). etcd accepts only TLS 1.3 client certificates with the shared `etcd:member` identity (the Armada API refuses it) and listens on the server's private IP, never publicly; the member certificate names every private address of the machine (do not skip etcd's client SAN check). Transactions delete many keys by range (`etx.deleteRange`/`deletePrefix`, one operation each; no write into a deleted range in the same transaction): `DeleteApp`, `DeleteJob`, and the audit trim; etcd allows `maxTxnOps` (4096) operations per transaction (`internal/etcd`); tests see each commit's operation count through `Etcd.onCommit`. A transaction reads one app's replicas by key prefix (`appReplicas`: deploys, revision pruning, `ListReplicas` with an app, app and job removal, job runs): replica IDs start with `<app>-` (`replicaPrefix`, enforced by `CreateReplica`), and the record's app still decides, since `web-` also holds `web-api`'s; tests see each list's key count through `Etcd.onList`. Domain claims and pruning still read every live spec (`liveSpecs`): a domain record names its project, not the apps that route it. A reconcile pass logs an app it cannot reconcile, records `ReconcileFailed` once (a condition), and goes on with the others; only `ErrNotLeader` or a cancelled context end the pass. `SetNodeStatus` writes nothing when only a LastSeen less than `nodeSeenEvery` (30s) newer changed, so agent reports do not move the commit key under every other transaction. Incompatible record changes bump `etcdSchema` with a migration; a binary refuses a newer schema. Tests use a shared embedded member per package (`store/storetest`, `TestMain`). Reads of many revisions go through `getMany` (`GetRevisions`, `revisionCache.preload`, `ListApps`, `liveSpecs`): read-only transactions of `readBatch` gets at the snapshot revision. Do not add dependencies that need CGO. A new file in the data directory must be added to `internal/backup` (a test checks the layout).
- Control plane topology (ADR 0010): one server is supported, three are recommended. Servers elect a leader through etcd (`etcd.Campaign`); only the leader serves the API/join listener and runs reconcilers and certmagic, each term with a fresh `server.Server` and a store fenced on the election key (`Etcd.Fenced`, `ErrNotLeader`). Servers join with a single-use server token (`token create --server`, `server join`), which hands over the CA and master keys; new members start as etcd learners and are promoted by the leader. Agents and the CLI hold every server address and dial with `pick_first`. ACME data lives in etcd (`certs.EtcdStorage`, `/armada-acme/`).

## Code conventions

- Everything is in **English**: code, identifiers, comments, commit messages, error messages, and all documentation (open source project for a global audience).
- Commit subjects follow Conventional Commits, `type(scope)!: description`, because the release notes are grouped by type (`.goreleaser.yaml`) and CI rejects other subjects (`scripts/check-commits.sh`). Types: `feat`, `fix`, `security`, `perf`, `docs`, `deps`, then `refactor`, `test`, `ci`, `build`, `chore`, `style`, `revert`; `!` marks a breaking change. Write the description for the people reading the release notes. `main` only changes through pull requests that pass every CI job (repository ruleset; see docs/releasing.md).
- Idiomatic Go: `context.Context` as the first argument for I/O, errors wrapped with `fmt.Errorf("...: %w", err)`, logging with `log/slog`.
- All code lives in `internal/` except the protobuf definitions in `api/` (Armada has no public Go API).
- YAML specs are parsed strictly (unknown field = error). Features whose types exist but are not implemented yet must be rejected with a clear message, never silently ignored.
- Tests live next to the code (`_test.go`). Reconciler logic is tested with fake drivers/stores, not a real runtime. HAProxy renderer changes require golden files.
- Development and CI always use ACME staging or Pebble, never the Let's Encrypt production endpoint.

## Keeping documents current (mandatory)

Every change updates, in the same commit or pull request, every document it makes stale. A change is not done until its documents are; do not leave it for a follow-up. Before committing, check at least:

- `README.md`: the feature list, the tested environments table, and the document links.
- `CLAUDE.md`: Status, Commands, Architecture in brief, and these conventions.
- `docs/`: quickstart, operations guide, spec reference, `threat-model.md` for anything that changes the attack surface or a mitigation, and `docs/adr/` for design decisions (a new ADR, or an update to the one the change supersedes, plus the index in `docs/adr/README.md`).
- CLI help text and error messages that describe the changed behaviour.

## Security rules (mandatory)

This is infrastructure software that holds root on every node. Treat these rules as merge requirements, not suggestions:

1. **Never weaken mTLS** (no `InsecureSkipVerify`, no `--insecure` flag, no plaintext fallback), including for development or tests.
2. **User input into the HAProxy configuration** (domains, paths, app names) must pass whitelist validation in `internal/spec` and be validated again in the renderer. Never interpolate user strings into templates without validation, and never turn them into regular expressions.
3. **Secrets:** never print plaintext to logs, errors, CLI output, or the audit log. Secret types must redact themselves through `String()`/`LogValue()`. Never accept secret values as CLI arguments (they end up in shell history); read them from stdin or a file.
4. **Bind interfaces:** agent/server gRPC, internal DNS, HAProxy stats, and container ports bind only to private IPs. Only HAProxy on ports 80/443 faces the public. Never bind internal services to `0.0.0.0`.
5. **Sensitive files** (CA key, master key, TLS private keys, `~/.armada/config`, state DB) are created with `0600`/`0700` permissions. Check permissions when reading them.
6. **Cryptography:** use Go's standard `crypto/*` packages and `crypto/rand`. Never invent cryptographic schemes. Compare tokens with `subtle.ConstantTimeCompare`. Store join tokens only as hashes.
7. **Secure container defaults:** `no-new-privileges`, no `--privileged`, no host network, no container runtime socket mount, memory/PID limits. Any relaxation must be explicit in the spec.
8. **System images** (HAProxy) are pinned by digest, not by tag.
9. **Authorization** is based on the identity in the client certificate: an agent may only access agent RPCs and data for its own node.
10. Changes touching `internal/pki`, `internal/secrets`, `internal/certs`, the proxy renderer, or API auth must come with tests for negative cases (malicious input, wrong certificates, expired tokens) and, where relevant, an update to `docs/threat-model.md`.

If a request conflicts with these rules, explain the risk and offer a safe alternative before doing the work.
