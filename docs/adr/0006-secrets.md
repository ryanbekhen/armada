# 0006. App secrets: envelope encryption, pinned versions, tmpfs files

- Status: Accepted
- Date: 2026-10-31

## Context

Apps need credentials (database passwords, API tokens, TLS keys, registry passwords) without putting them in the spec, the state database, logs, or shell history. The control plane state (etcd, and the backups operators copy around) must be safe to leak on its own. Revisions are immutable and rollbacks must reproduce what ran before, which includes the secret values.

## Decision

- **Scope.** Secrets belong to an app and are addressed as `APP/NAME`; names follow the same rules as DNS labels. They can be set before the app's first deploy.
- **Envelope encryption.** A 256-bit master key is generated by `armadad init` (`master.key`, mode `0600`). Each secret version is encrypted with a fresh random data key using AES-256-GCM, and the data key is encrypted with the master key, also AES-256-GCM. Both layers bind `app`, `name`, and `version` as additional data, so ciphertexts cannot be moved between apps, secrets, or versions. Only Go's standard `crypto/*` packages are used. The state database records the master key's ID, and the server refuses to start with a different or missing key instead of silently creating secrets nobody can decrypt.
- **Write-only values.** `armada secret set` reads from a hidden terminal prompt, stdin, or `--from-file`, never from an argument. No RPC returns a value; `secret list` shows names, versions, and which revisions use them. Plaintext is held in `secrets.Value`, which redacts itself in every `fmt` verb, `slog`, and JSON.
- **Pinned versions.** Every `set` creates a new version. A deploy pins the latest version of each referenced secret into the revision, and a deploy fails if a referenced secret is not set. Setting a secret that the app's current revision uses rolls the app out as a new revision with the new version (opt out with `--no-rollout`). A rollback runs the versions its revision pinned. Versions that are neither the latest nor pinned by a retained revision are deleted. A secret used by the active or target revision cannot be deleted.
- **Delivery.** The server decrypts pinned versions only while building the assignment for the node that runs the replica, and sends them over mTLS. If decryption fails, the node's whole assignment is withheld, so the agent keeps what is running rather than stopping replicas.
- **Three ways to consume a secret:**
  - `env[].secretRef`: an environment variable.
  - `secretFiles[]`: the agent writes the value to its secrets directory (default `/run/armada/secrets/<replica>/`, which must be tmpfs or ramfs; root-owned, `0700`) and bind-mounts the file read-only. If the directory is not memory-backed, the agent disables secret files and such replicas fail with a clear message.
  - `registry.passwordSecretRef`: credentials for pulling the image from a private registry; the registry must match the image's.
- **No plaintext in fingerprints.** The agent's spec hash, stored as a container label, replaces secret values with their `name@vN` reference.

## Rejected alternatives

- **Secrets referenced by name only, resolved at run time.** Simpler, but a rollback would run the new value, and a secret change would silently apply to some replicas (those restarted) and not others.
- **Rolling out on every `set`, including secrets the app does not use.** Needless restarts; only revisions that reference the secret are rolled.
- **Writing secret files into the container's filesystem or onto a tmpfs mount inside it.** Files copied into the container's filesystem land in its writable layer on disk, and copying into a tmpfs inside a running container is not reliable; host tmpfs plus a read-only bind mount is simple and keeps plaintext off disk.
- **A `secret get` command.** Convenient, but every read path is a leak path. Operators keep the source of truth for a value elsewhere; Armada only needs to deliver it.
- **KMS or an external vault for the master key.** Out of scope for v0.1; the key file can later be replaced by another key source behind `secrets.Keyring`.

## Consequences

- Backups need both the state and `master.key` (`armadad backup` takes both); losing the key loses every secret. `armadad init` says so.
- Environment-variable secrets are stored by the container runtime in the container's configuration on the node's disk and are visible to root on that node. `secretFiles` avoid both and are recommended for sensitive values.
- Secret files are world-readable inside the container (mode `0444`) so any container user can read them; isolation on the host comes from the root-only parent directory.
- The server keeps decrypted values in memory for the assignments it holds, and the agent for the replicas it runs.
- protobuf-go does not honor `debug_redact`, so messages carrying secrets must never be logged; tests grep the server log, CLI output, state database, and container labels for planted values.
