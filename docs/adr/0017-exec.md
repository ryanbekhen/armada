# 0017. Running commands in replicas

- Status: Accepted
- Date: 2026-11-03

## Context

Debugging an app often needs a look from inside one of its containers: a
shell to read a generated file, check DNS from the container's point of
view, or run the app's own maintenance command. Logs show what an app
writes, not what its environment looks like. Today an operator has to find
the node that runs a replica, log in to it, and use the runtime's own tools,
which bypasses Armada's authorization and leaves no record.

Every other operation goes through desired state: the CLI writes it, and
reconcilers converge. Running a command is different in kind: it changes no
desired state, and its result is a stream of output and an exit code, like
`armada logs`.

## Decision

`armada exec APP [--replica ID] [-i] [-t] -- CMD [ARG...]` runs a command in
one replica of an app and returns its exit code.

- Without `--replica`, the server picks a running, ready replica of the
  serving revision. `-i` passes the CLI's standard input; `-t` allocates a
  terminal (raw mode in the CLI, window size changes forwarded), so
  `armada exec web -it -- sh` gives an interactive shell. Without `-t`,
  standard output and standard error stay separate.
- Exec is a diagnostic channel, like logs, and not a way to change an app:
  what a command changes inside a container is lost when the replica is
  replaced. The documentation says so.

### Path

The path follows `armada logs`; no new listener is opened anywhere.

1. The CLI opens `AdminService.Exec`, a bidirectional stream, and sends the
   request first: app, optional replica, command, and the terminal and
   standard input flags.
2. The server authorizes the admin certificate, picks the replica, records
   the session in the audit log, and offers an `ExecRequest` with a random
   request ID to the replica's node over its control stream.
3. The agent checks the replica is assigned to it and has a container, then
   opens `AgentService.ExecSession`, a bidirectional stream whose first
   message names the request. The server accepts the stream only from the
   node the request was sent to, once.
4. The agent runs the command through the runtime and relays input,
   terminal size changes, output, and finally the exit code. The server
   relays between the two streams. Either side ending the session ends it.

### Runtime

- `runtime.Execer` runs a
  command in an app container with optional standard input, an optional
  terminal and its size changes, and returns the exit code. It is separate
  from `SystemRunner.Exec`, which only serves Armada's infrastructure
  containers and returns combined output.
- The process gets the container's own security context: user,
  capabilities, `no-new-privileges`, seccomp, cgroup limits, and
  namespaces. Nothing in the request can change them; there is no
  privileged or root option.
- The runtime refuses exec in Armada's system containers and re-checks the
  command.
- The conformance suite checks standard input, separate streams, the exit
  code, the terminal and its size changes, and that the exec process keeps
  the container's security defaults. A terminal's initial size may reach
  the command a moment after it starts, as with engines that apply it only
  then; the suite waits up to two seconds for it.

### Limits

- A command has at most 64 arguments of at most 4096 bytes, without NUL
  bytes; messages carry at most 32 KiB of data.
- An agent runs at most 8 sessions at once, and the server ends a session
  after 30 minutes without input or output.
- The audit log records the admin, the app, the replica, the command's
  name, and whether a terminal was used, but not the arguments, which can
  hold secret values. Session errors never include the arguments; an error
  from the runtime may name the program, as the audit log does.

## Alternatives considered

- **A direct connection from the CLI to the node**: needs a listener on
  every node, its own authorization, and the CLI's access to the private
  network. The server relay keeps nodes free of listeners and reuses the
  admin certificate check.
- **Only non-interactive commands**: smaller, but most debugging needs a
  shell, and the stream protocol is the same either way.
- **Exec through `SystemRunner.Exec`**: it returns combined output only and
  serves infrastructure containers; mixing app containers into it would
  blur the line ADR 0011 draws between them.

## Consequences

- Admins can run any command in any replica: an admin certificate already
  controls every app's image and secrets, so exec adds no new authority,
  but it is a powerful one and is audited.
- Each session holds two streams through the leader; sessions end when the
  leader changes, like log streams.
