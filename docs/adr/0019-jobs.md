# 0019. Jobs

- Status: Accepted
- Date: 2026-11-03

## Context

Apps run until they are replaced. Clusters also need work that runs to
completion: database migrations, backups, reports, cleanups, on demand or
on a schedule. Without jobs, operators keep a cron entry on one machine,
which defeats placement, secrets, logs, and self-healing.

The spec format has reserved `kind: job` from the start and rejected it
until now.

## Decision

A job is a spec of `kind: job`. Each run starts one container that runs to
completion. Runs start on demand (`armada job run`) or on a cron schedule,
or, since ADR 0040, while a queue holds messages.

### Spec

```yaml
kind: job
name: db-backup
image: ghcr.io/acme/backup:1.4
command: ["/backup.sh"]
schedule: "0 3 * * *"     # optional: five cron fields
timeZone: Asia/Jakarta     # optional, default UTC
timeout: 30m               # per attempt; default 1h, at most 24h
retries: 2                 # default 0, at most 10
concurrency: forbid        # forbid (default) or replace
history: 5                 # finished runs kept; default 5, at most 50
tasks: 10                  # optional: split each run into 10 tasks
parallelism: 3             # optional: at most 3 at once; default all
```

- `env`, `secretFiles`, `registry`, `resources`, and `placement` work as
  for apps.
- `ingress`, `probes`, `scale`, and `revisions` are rejected.
- Schedules have five fields (minute, hour, day of month, month, day of
  week). Descriptors (`@daily`) and `CRON_TZ=` are rejected; `timeZone`
  sets the zone. Time zone data is built into the binary.
- Jobs and apps share one namespace: deploying an app under a job's name,
  or the other way round, is refused.

### Desired state

- A job is stored like an app, with revisions that pin its secret
  versions, but with no rollouts: a deploy makes the new revision current
  at once, and new runs use it. `armada secret set` rolls a job forward the
  same way. `scale` and `rollback` refuse jobs, and `armada status` leaves
  them out.
- A run is a record under `runs/<job>/<number>`. It is `pending`,
  `running`, `succeeded`, `failed`, or `cancelled`, and records the trigger,
  revision, attempts, node, exit code, and times. Run numbers are never
  reused.
- With `tasks`, a run holds that many tasks (`RunTask`: index, state,
  attempts, latest replica and node, exit code, message), each with its
  own attempts; the run's attempts, node, and replica name the latest
  attempt of any task. Schema 12.
- Each attempt of a run is a replica record marked with its run (and its
  task). Attempts
  go through the usual assignment path, so placement (`eligible()`),
  capacity reservations, secrets, image digests, logs, and `armada top`
  work as for apps.

### The leader

On every reconcile, for each job, the leader:

- **Schedules.** It counts from the latest fire, or from the current
  revision if that is newer, so a new schedule does not fire for times
  before it existed.
  - The latest due fire starts a run. The job records that time in the same
    transaction (`LastScheduled`), so a fire runs once even across leader
    changes.
  - A fire more than an hour late (the control plane was down) is skipped
    and recorded as a `Missed` event.
  - With `concurrency: forbid`, a fire while a run is active is skipped
    (`Skipped`). With `replace`, the active run is cancelled first.
- **Places attempts.** A pending run's attempt goes to a node that its
  placement allows, that has the capacity, and whose agent runs jobs.
  - If no node fits, the run waits, with an `Unschedulable` event. It fails
    if no node fits within its timeout.
- **Watches attempts.** An attempt ends when its container exits, it fails
  to start, its node is lost, or its timeout passes. The timeout counts
  from placement, so it includes pulling the image.
  - A non-zero exit or any of the other endings is retried while retries
    remain, after 10s, 20s, 40s, and so on up to 5 minutes, possibly on
    another node.
  - Two attempts of one run never run at the same time.
- **Prunes.** It keeps the newest `history` finished runs. The container of
  a finished run is kept for 24 hours, so `armada logs` can show its
  output, and is then removed. Only the latest attempt's container is kept.

**Tasks.** For a run with tasks, the leader does the same per task: it
starts pending tasks in index order while fewer than `parallelism` run
(spread over nodes like an app's replicas), retries a task that ended
badly on its own, and counts a task's wait for a node only while it has a
place in the parallelism. The run succeeds when every task succeeded. It
fails, with the task's exit code and message, once a task has no retries
left; the other tasks are then cancelled and their containers stopped.
Each container gets `ARMADA_JOB_TASK` (its index) and `ARMADA_JOB_TASKS`.
Splitting the work by index needs no coordination between tasks, which is
why tasks are indexed rather than a count of identical containers.

Manual runs follow the concurrency policy too: `armada job run` refuses
while a run is active under `forbid`, and cancels it under `replace`.

### The agent

- An assignment marks an attempt's replica with `JobAttempt`.
- The agent starts the container once and never restarts it. When the
  container exits, the agent reports `finished` with its exit code. It
  keeps reporting the same result, and the leader keeps the first.
- When the leader marks the attempt `done` (finished, timed out,
  cancelled, or its node lost), the agent stops the container if it still
  runs, never starts it again, and keeps it for its logs. `done` is not
  part of the spec hash.
- A container left created but never started has not run the job, so it is
  started afresh.
- Agents announce `jobs` in their hello. Runs are placed only on nodes
  that do, so an older agent never restarts a job's container forever
  during an upgrade.

### Upgrades

The state schema moves to 3 with no rewrite. Servers that would treat a job
as an app can no longer lead once it moves (ADR 0012).

### Interfaces

- `armada job run|list|runs|cancel|remove`
- `armada logs JOB [--run N]`
- `AdminService.RunJob`, `ListJobs`, `ListJobRuns`, `CancelJob`, and
  `DeleteJob` (admin only)
- Events of kind `job`: `Deployed`, `Started`, `Succeeded`, `Failed`,
  `Retrying`, `Cancelled`, `Skipped`, `Missed`,
  `Unschedulable`, `Deleted`
- Metrics:
  - `armada_job_runs_total{job,result}`
  - `armada_job_runs_active{job}`
  - `armada_job_last_success_timestamp_seconds{job}`

## Alternatives considered

- **A job as an app with a restart policy**: fewer concepts, but runs,
  retries, history, and schedules would all hang off a type built for
  long-running replicas.
- **Agents run schedules**: no leader involvement, but a schedule would
  depend on one node being up, and two nodes could run the same fire.
- **Run every missed fire after an outage**: faithful to the schedule, but
  a long outage would start a burst of runs that nobody wants.
- **Keep every attempt's container**: complete logs, but a crash-looping
  job with retries would fill a node's disk with stopped containers.

## Consequences

- Runs are at least once. An agent that restarts after the container has
  exited but before the leader saw it may start the job again if the
  container is gone. A partitioned node keeps running an attempt the
  leader has given up on, so its retry may overlap it. Jobs should be
  idempotent.
- Runs are not moved off cordoned nodes; they finish where they are.
- A job's secrets stay after the job is deleted, like an app's.
- Dependencies between jobs, several containers per run, and running a job
  before an app's rollout are not part of this decision.
