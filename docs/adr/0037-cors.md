# 0037. Cross-origin requests at the proxy

- Status: Accepted
- Date: 2026-11-11

## Context

A browser on one origin (`https://app.example.com`) that calls an API on
another (`https://api.example.com`) first asks the API whether it may
(a preflight `OPTIONS` request), then reads the answer only if the response
says so (`Access-Control-Allow-Origin`). Every API that serves a web app on
another origin needs this. It is easy to get wrong in each app: answering
`*` together with credentials, or reflecting any `Origin` back.

## Decision

`ingress.cors` on apps with ingress:

```yaml
ingress:
  cors:
    allowOrigins: [https://app.example.com, http://localhost:3000]   # or ["*"]
    allowMethods: [GET, POST]                     # default GET, HEAD, POST
    allowHeaders: [Content-Type, Authorization]
    exposeHeaders: [X-Request-Id]
    maxAge: 10m                                   # how long browsers keep a preflight answer
    allowCredentials: true                        # cookies and Authorization from the browser
```

- **Validation.**
  - Origins are `http://` or `https://`, a lowercase host name or
    `localhost`, and an optional port, with nothing else; at most 32.
  - `*` stands alone and never with `allowCredentials`, which browsers
    would refuse anyway.
  - Methods come from a fixed list. Header names are letters, digits, and
    hyphens. `maxAge` is at most 24 hours.
  - The proxy's `Validate` checks every value again, and the single-token
    check covers them, because they are written into HAProxy's
    configuration (security rule 2).
- **Preflight.** At the start of each of the app's backends (labels and
  wake included), HAProxy sets `txn.cors` to the request's `Origin` when the
  origin is listed (or to `*` for an open policy). An `OPTIONS` request
  with `Access-Control-Request-Method` from such an origin is answered
  `204` by the proxy, with the allowed methods, headers, max age, and
  credentials, and never reaches the app or wakes one scaled to zero.
- **Responses.** For allowed origins, the proxy adds
  `Access-Control-Allow-Origin` (the exact origin, never a reflection of
  an unlisted one), `Access-Control-Allow-Credentials`, and
  `Access-Control-Expose-Headers` to the app's responses, and to the
  proxy's own (`http-after-response`): a `503` while no replica is up, or a
  `403` from the address rules, so the browser shows the real status instead
  of a CORS error. Every response gets `Vary: Origin`, so caches keep answers
  for different origins apart.
- **Other origins.** Requests from other origins get no CORS headers, so
  browsers refuse to let their pages read the answer.
- **Rules that run first.** Client address rules (ADR 0035) run before CORS,
  so a refused client gets `403` for its preflight too.
- **Changing it.** `armada app create`/`update --cors-origin` (repeatable,
  replaces the origins and keeps the rest of the policy) and `--no-cors`.
  The other fields are set in the spec file. A change reloads the proxy.

## Consequences

- **The app's own CORS headers.** An app that sets its own CORS headers gets
  them overwritten (`Allow-Origin`, `Allow-Credentials`,
  `Expose-Headers`) for listed origins. Use one place.
- **No wildcard subdomains** (`https://*.example.com`). Each origin is listed
  on its own, up to 32.
- **CORS is not access control.** It only tells browsers what pages may read.
  Any other client can call the app regardless. Use `ipAllow` (ADR 0035)
  or the app's own authentication to keep callers out.
