# Tested environments

Every release is tested end to end on real machines with [test/e2e](../test/e2e/README.md). These are the environments Armada has been run in.

| Environment | Status |
| --- | --- |
| Cloudflare DNS-01 with Let's Encrypt staging | Tested on depa.id (amd64, Ubuntu 24.04): certificates for the root domain and a wildcard, domain verification, challenge records removed afterwards, the token kept out of logs and events, and requests through the Cloudflare proxy with trusted proxies (the client's address kept, forged headers from elsewhere dropped) |
| Local lab: Linux VMs (arm64), Pebble ACME, 1–2 nodes | Tested end to end: deploys, rolling update, secret files, internal ingress and DNS, crash recovery, agent restart with containers kept running, reboot recovery, rolling upgrade with a state migration, rebalancing after a drained node resumed under HTTPS load without errors, replicas across nodes |
| Oracle Cloud (arm64, Oracle Linux 9, SELinux enforcing), one server, Let's Encrypt staging | Tested end to end with releases before the beta: install.sh with systemd, doctor, wildcard certificate over Cloudflare DNS-01, rolling update under load without errors, crash recovery, reboot recovery, SELinux-confined apps and HAProxy, HAProxy restarted after a crash. Containers on crun (the beta's only OCI runtime) are not tested on arm64 or under SELinux yet |
| depa.id (amd64, Ubuntu 24.04), three control plane servers and one node, Let's Encrypt staging | Tested end to end with [test/e2e](../test/e2e/README.md): server and node joins, only HAProxy public, certificates on every node, secrets, rolling update, rollback, and agent restart under load without errors, leader stop and SIGKILL under load, node loss and rebalancing under load, backup, all machines rebooted at once |
| Mixed architectures: three depa.id servers (amd64, Ubuntu 24.04) and an Oracle Cloud node (arm64, Oracle Linux 9, SELinux enforcing), Let's Encrypt staging | Tested end to end with [test/e2e](../test/e2e/README.md) with releases before the beta: every scenario above except the reboot, plus placement under load and images built for one architecture running only on nodes of that architecture |
| depa.id (amd64, Ubuntu 24.04, kernel 6.8), two machines on a private network, `--network wireguard` | Tested: the kernel WireGuard device on both nodes, handshakes in `armadad doctor`, requests between replicas on different nodes, only encrypted traffic on the private network, the tunnel staying up while an agent is stopped, the same key after an agent restart, and recovery after a node reboot |
| depa.id (amd64, Ubuntu 24.04), machines with only public addresses, `--network mesh` | Tested: `init` on one machine with the endpoint found on its own; a node joining with `join-token --from`, and two servers joining as control plane servers, each getting a mesh address; the join port closed without a token, open while one is, closed again once it is used, and the API port never public; doctor's kernel WireGuard and handshakes; replicas on different nodes reaching each other through the mesh; the leader stopped and another taking over; one machine rebooted, then all three at once, with the cluster and its app back on their own |
| depa.id (amd64, Ubuntu 24.04), two machines on a private network, switching modes | Tested: a `plain` cluster switched to `wireguard` (30 s) and back to `plain` (26 s) with `armada cluster update --network`, while a container on one node called an app on the other five times a second through the internal frontend: no request failed in either switch; `armada cluster status` showed each step and the peers a node did not reach yet; afterwards `armada-net` was the new tunnel on both nodes, `armada-next` gone, `agent.json` and doctor on the new mode; a switch given up while preparing left both nodes on `plain` |
| depa.id (amd64, Ubuntu 24.04), sites: two machines on a private network, one from another site with a private network of its own, and a control plane server from a third site with no private network | Tested: a `plain` cluster on the private network; a node joining from site `far` over the leader's public address with its own private IP, the join port open only while the token was and closed again once it was used; a control plane server joining from site `cloud` with a mesh address and serving the API; apps pinned to each site with `armada.site` answering a load from the first site through the internal frontend (the first request of the load's container failed, at its start and again after the reboot: a container's first call before its node knew it, fixed since; no other request failed); doctor's handshakes on `armada-wg`, its check that no other site's address lies in a local network, and its warning once one did; all four machines rebooted at once, with the cluster, the second server, and the apps back on their own |
| Local lab, depa.id, and a three-server production cluster (amd64, Ubuntu 24.04) | Tested for v0.1.0-beta.1: every end-to-end scenario on local VMs and on depa.id (235 checks each); the lab upgrade from v0.1.0-alpha.44 under load ([test/e2e/upgrade.sh](../test/e2e/upgrade.sh)); the production cluster upgraded from v0.1.0-alpha.43 through v0.1.0-alpha.44 to v0.1.0-beta.1 one server at a time under live traffic, its containers moved to crun one replica of an app at a time: of 1,404 probes through the public endpoints and each server's own address, 2 failed (a 404 through one server's address while the leader's proxy configuration lacked the root domain's hosts for about 1.5 s after a slow etcd read, fixed since), doctor clean on every server afterwards, and an app that scales to zero woken |
| Containers of Ubuntu 24.04, Debian 12, Rocky Linux 9, AlmaLinux 9, Oracle Linux 9, Fedora 41, openSUSE Leap 15.6, and Alpine 3.20 | Tested: `init` and `server join` add the user who ran them through sudo to the `armada` group with the distribution's own tool (`usermod`, or BusyBox `addgroup` on Alpine), also when sudo's PATH lacks the sbin directories, and only once |
| armada-kv preview (`armadad init --state kv`, ADR 0057), one machine without root | Tested on loopback only, not on real machines yet: init, `armadad kv` and `armadad server` over armada-kv's mutual TLS, secrets and an app written and read back through the client, the state kept across a restart of `armadad kv`, a second `armadad kv` refused, `armadad etcd` and `armadad backup` refusing such a server; two members joined and promoted over mutual TLS in process (`kv/tests/tls.rs`). `armadad server join` to such a cluster is untested end to end |
| The move from etcd to armada-kv (ADR 0057), in process | Tested in process only, not on real machines yet (`server/tests/replay/statemove.rs`): one server and three on the pinned etcd moved to armada-kv members in the test's process, the key spaces equal at the move's revision, every member voting and holding the whole key space on its own (also with the first member stopped), the server records naming armada-kv's member IDs, every server told to switch, writes refused on etcd and working on armada-kv; a member that does not join leaving the cluster on etcd with writes working and the next try backed off; writes refused while copying; a new term giving up a move left half done. armada-kv backups taken and restored in process |

Reports from other providers are welcome.
