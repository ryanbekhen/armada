# Armada Threat Model (v0.1)

Status: draft, 31 Oct 2026. Updated whenever PKI, secrets, certificates, the proxy renderer, or API authentication change (see the security rules in CLAUDE.md).

Method: STRIDE per trust boundary.

## 1. System being modeled

```
                Internet
                   │  80/443
        ┌──────────▼──────────┐        private network (VPC)
        │  HAProxy (per node) │◄──────────────────────────────┐
        └──────────┬──────────┘                               │
                   │ private IP : host port                   │
        ┌──────────▼──────────┐   gRPC mTLS   ┌───────────────┴──┐
        │ app container       │               │  armadad server  │◄── armada CLI (mTLS)
        └──────────▲──────────┘               │  (state, CA,     │
                   │ containerd (root)        │   certmagic)     │
        ┌──────────┴──────────┐   gRPC mTLS   └──────────────────┘
        │   armadad agent     ├──────────────────────►
        └─────────────────────┘   (agent initiates the connection)
```

## 2. Assets

| Asset | Location | Impact if leaked |
| --- | --- | --- |
| Cluster CA key | server data directory; backup archives | Attacker can issue node/admin certificates → full control of the cluster |
| Secret master key | server data directory (`master.key`, `0600`); backup archives | All app secrets exposed (together with the state) |
| Decrypted secrets | server memory; agent memory; node tmpfs (secret files); the runtime's container config on node disk (env secrets) | That app's credentials exposed |
| Admin certificate | `/etc/armada/admin.config` on the first server (root, readable by the `armada` group); `~/.armada/config` of the user who ran `sudo armadad init` and of each person given one | Full control of the cluster: every member of the `armada` group on that server holds it |
| DNS provider token | In the state, sealed with the master key (ADR 0031); clusters from before keep a `0600` file on the server until its leader moves it over | Domain hijacking |
| Registry credentials | store (encrypted, as an app secret) | Theft of private images |
| Domain TLS private keys | certmagic storage, PEM on every node | Eavesdropping on/impersonation of user sites |
| Container runtime socket (embedded containerd at `/run/armada/containerd/containerd.sock`) | every node | Root on the node |
| State (embedded etcd, `etcd/` in the data directory) | server; backup archives (as a snapshot) | Cluster topology, metadata; secret ciphertext; writing to it controls what every node runs |
| etcd member key | server data directory (`etcd/member.key`, `0600`) | Read and write access to the state, from wherever the member's address is reachable |
| Server join token | shown once by `armada server join-token`; stored only as a hash | While valid (single use, at most 1 h): redeemable for the CA key and the master key |

## 3. Threat actors

1. **Internet attacker**: can only reach HAProxy on 80/443.
2. **Other VPC tenant**: another machine on the same private network (owned by the same user but compromised, or a provider misconfiguration).
3. **Compromised app**: malicious code inside one of the containers Armada runs.
4. **Compromised node**: an attacker gains root on one agent machine.
5. **Supply chain**: tampered Go dependencies, HAProxy image, bundled runtime binaries (containerd, runc, CNI plugins, tini), or release artifacts.

## 4. Threats and mitigations

| # | Boundary | STRIDE | Threat | Mitigation | Status |
| --- | --- | --- | --- | --- | --- |
| T1 | Internet → HAProxy | Tampering / EoP | HAProxy config injection via user-supplied domain/path/app name, or via addresses reported by a node | Whitelist validation in `spec`, revalidated in `proxy.Config.Validate` (agent) before rendering; user input is used only as literal strings (`-m str`/`-m beg`, prefix stripping by segment count, no regex); IP addresses must be canonical and carry no IPv6 zone (a zone may hold any bytes, including newlines); the renderer refuses to emit a configuration if any interpolated value is not a single token (no whitespace or control characters); golden tests, `FuzzRender` fuzzing, `haproxy -c` before reload and in CI | Mitigated (phase 2, hardened in phase 7) |
| T2 | Internet → HAProxy | Spoofing | Custom domain hijacking (adding someone else's domain) | Verification of a TXT record `_armada-verify.<domain>` containing a random 128-bit per-domain token before routing and certificate requests; two apps cannot claim the same host+path | Mitigated (phase 2) |
| T3 | Internet → HAProxy | DoS | Exhausting ACME rate limits with arbitrary domains | Certificates are requested only for verified domains and `<app>.<root>`; certmagic's built-in backoff | Mitigated (phase 2) |
| T4 | Internet → internal services | Info disclosure | gRPC/stats/DNS/container ports exposed publicly | The API, join, ACME, metrics and DNS listeners and published container ports bind only to private addresses (`0.0.0.0`/`::`, public, and zoned addresses refused); auto-detection skips container and VM bridges; `armadad doctor` reports cluster ports listening on wildcard or public addresses, the host firewall state, and private-IP problems; internal ingress and DNS bind to the bridge gateway, not the private IP (ADR 0007). On providers with 1:1 NAT, anything on the private IP can still be reachable from the internet unless the provider firewall blocks it (see limitations) | Partially mitigated (phase 1, 6, 7) |
| T5 | VPC → server | Spoofing | Rogue node joins the cluster | Single-use join tokens (256-bit secret, 1 h default, at most 24 h) stored as SHA-256 hashes and compared in constant time; redeemed in the same transaction that registers the node; separate join listener that serves only `Join`, is rate limited and size capped; node names and private IPs validated (canonical, private, not loopback, no IPv6 zone), duplicates refused only after the token checks out so unauthenticated callers learn nothing about existing nodes; the CA chooses the certificate identity, not the CSR | Mitigated (phase 5, hardened in phase 7) |
| T6 | VPC → agent | Spoofing (MITM) | Rogue server during `join` | The join command carries the CA hash; `armadad join` learns the CA from the handshake, checks it against the pin and verifies the server certificate with it before sending anything (no `InsecureSkipVerify`); the token is read from a prompt, stdin, or a file, never from argv | Mitigated (phase 5) |
| T7 | VPC | Info disclosure | Eavesdropping on server ↔ agent traffic | Mandatory mTLS 1.3 with `RequireAndVerifyClientCert` on the main API, enforced at construction; no plaintext fallback or insecure flag | Mitigated (phase 1) |
| T8 | Compromised node → server | EoP | Agent requests another node's assignments/secrets, or a certificate for another identity | Authorization based on certificate identity; the server only sends data for that node; renewal always issues a certificate for the caller, whatever the CSR says | Mitigated (phase 5) |
| T9 | Compromised node | Repudiation / persistence | Stolen node certificate keeps being used | 30-day node certificates renewed automatically; serial allowlist checked on every RPC; a renewal revokes every other certificate of the node, so a stolen certificate dies at the next legitimate renewal; renewals are rate limited per node; `armada node delete` deletes the serials and closes the agent's stream; streams end when their certificate expires; certificates not issued by the server are refused. Nodes created before the allowlist existed accept any CA-signed certificate for their identity until their first renewal | Mitigated (phase 5, hardened in phase 7) |
| T10 | CLI → server | Spoofing | Unauthorized admin API access | API binds privately by default; mTLS with a user or service certificate; `0600` permission on the config. Each person has a user certificate under their own name (1 year, ADR 0028, ADR 0033); `armada rbac user delete` refuses every certificate of a name at once, `armada rbac user credentials` refuses the certificates a user was given before, including ones the old key renewed up to the second the replacement was recorded (it is bound by serial), and every API call and metrics scrape checks this. `armada rbac user renew` signs a new one only for a caller holding a valid user certificate, under the caller's own name, keeps its roles, is audited, is rate limited per user, and is checked and recorded in one transaction with any replacement, so a stolen key cannot renew past one; it gives a stolen certificate nothing it lacked. Renewing an expired one needs the CA key on a server (`armadad user renew`, root); a user certificate the cluster has no record of has cluster-admin, as only the CA signs one | Mitigated (phase 1, ADR 0028, ADR 0033) |
| T11 | Store | Info disclosure | Secrets readable from the DB, logs, CLI output, or the audit log | AES-256-GCM envelope encryption (random data key per version, wrapped by the master key); values are write-only (no RPC returns them); `secrets.Value` redacts itself in `fmt`, `slog`, and JSON; the audit log records only name and version; tests plant values and grep etcd's files (WAL, snapshots, database), the server log, CLI output, and container labels | Mitigated (phase 4) |
| T12 | Container → host | EoP | Container escape to the host | Always `no-new-privileges`, never privileged, host network, or a container runtime socket; memory limit (default 256Mi) and PID limit (1024); `NET_RAW`, `MKNOD` and `AUDIT_WRITE` dropped. The other default capabilities remain, containers run as the image's user (often root) and the root filesystem is writable | Partially mitigated (phase 1) |
| T13 | Container → container, node, platform | Info disclosure / EoP | A compromised app reaches another app's containers or internal service, another space's apps, the nodes, the control plane, the private network, or the cloud metadata service | With the cluster network (ADR 0025, ADR 0026): nftables tables on every node (`ip` and `bridge` families, rebuilt atomically) let traffic from one container address straight to another pass only between replicas of the same app, on one node and across nodes, and drop it towards unknown addresses; containers of every space but `default` (and of `default` once `armada space set default --network-isolation` is on) are kept from the private, shared, loopback, and link-local ranges, every node's private address, and every port of their own node except the DNS server on the bridge gateway and the proxy's ports 80 and 443; a container address the node does not know yet counts as isolated (fail closed); the agent's DNS server answers internal names only for the asking container's own space, and nothing for unknown addresses; HAProxy's internal frontend looks the caller's source address up in a map the agent keeps current through the Runtime API (validated again by the proxy driver: IPv4 in the node's subnet, valid app IDs, bounded size) and routes an internal name only for callers of the app's space, and with `ingress.allow` only for the listed apps of that space, so a forged `Host` header reaches nothing and unknown callers (including the node itself) get a 404. Addresses come from agents for their own replicas only, must lie in the node's own subnet (T21), and are validated again by every agent; an address two apps claim reaches nothing. Containers cannot forge their source address: they run without `NET_ADMIN` and `NET_RAW`. **Not covered:** clusters without the cluster network are not filtered (their published ports bypass `ingress.allow`). Containers of every space share the node's kernel, so a kernel bug reachable from a container crosses this boundary: Armada does not contain code from people the operator does not trust, which needs a cluster of its own or dedicated nodes | Partially mitigated (ADR 0026) |
| T14 | Supply chain | Tampering | Tampered binary/installer/image | Release workflow (GoReleaser) runs the CI gates, then publishes sha256 checksums, an SBOM per archive, a keyless cosign signature bundle of the checksum file, and GitHub build provenance; `install.sh` refuses archives whose checksum does not match and verifies the signature against the release workflow identity for that tag when cosign is installed (`ARMADA_REQUIRE_SIGNATURE=1` makes it mandatory), and `armadad upgrade` does the same checks before it replaces anything (HTTPS only, redirects included, or a `file://` mirror; only `armadad`, `armada`, and `deploy/systemd/armada-*.service` taken from the archive; no downgrades; ADR 0030); piped into `sh`, the installer runs nothing until the whole script has arrived (its body is a function called on the last line); CI actions pinned by commit SHA; HAProxy image pinned by digest; govulncheck, gosec and Dependabot | Mitigated (phase 7; first signed release pending) |
| T15 | Server | Repudiation | Untraceable changes | Audit log with identity from the client certificate; automatic changes (rollout completed/failed) recorded with actor `system` | Partial (deploy, scale, root domain, rollback, rollout, secret set/delete, join token, node join/cordon/label/restrict/remove) |
| T16 | Server → agent | Info disclosure | App TLS private keys leak during distribution or on node disk | Sent only over mTLS, in the assignment or, for current agents, fetched by reference with `GetCertificates`, which only node certificates may call and which answers only names the cluster serves (each checked against the SHA-256 the assignment names); written `0600` in a `0700` directory; never logged (the agent does not print `ProxyConfig`). Every node, including a newly joined one, receives the private key of every public domain, because any node can receive public traffic | Mitigated (phase 2) |
| T17 | VPC → server | Spoofing / DoS | ACME HTTP-01 responder abused | Binds only to a private IP (port 0/`0.0.0.0` rejected); answers only active challenge tokens, 404 otherwise | Mitigated (phase 2) |
| T18 | Host | Info disclosure | DNS provider token leaks (shell history, DB, logs) | Read from a `0600` file (`--dns-token-file`), not stored in the DB, never shown in errors | Mitigated (phase 2) |
| T19 | Node | EoP | HAProxy Runtime API (admin level) used by another process | Socket in a root-owned `0700` directory, mode `600`; no TCP listener | Mitigated (phase 2) |
| T20 | Server → agent | SSRF / Tampering | A compromised server (or malicious spec) uses agent probes to send requests to other addresses on the node's network | The agent only probes the container's own IP (bridge IP, or the app's published port); probe paths are revalidated on the agent with the same whitelist as the spec; the probe client does not follow redirects and ignores `HTTP_PROXY`; at most 4 KiB of the response body is read | Mitigated (phase 3) |
| T21 | Agent → server | Tampering / DoS | A compromised agent reports fake "ready" replicas to pull traffic to other containers, blocks rollouts, or breaks the proxy configuration of the whole cluster | Reports only apply to replicas belonging to that node; addresses must be exactly `<node private IP>:<port>`, or with the cluster network (ADR 0025) an address in that node's own subnet other than its network, gateway, and broadcast addresses, in canonical form with a non-zero port, and a reported container address (which every node's firewall keys on, T13) likewise only in that node's subnet; `ready` is accepted only in state `running`; a server whose address still fails validation is left out of its backend instead of failing the whole configuration; HAProxy still runs its own health checks. A compromised agent can still serve any content from its own node (the "agent = root" limitation) | Partially mitigated (phase 3, hardened in phase 7) |
| T22 | CLI → server | Tampering | Rollback to another app's revision, or a rollback that grabs a domain already used by another app | The revision must belong to the same app; rollback goes through the same host+path conflict check as deploy and re-registers domains with TXT verification | Mitigated (phase 3) |
| T23 | Store | Tampering | Someone with write access to the DB swaps ciphertexts between apps, secrets, or versions so one app receives another's secret | App, name, and version are bound as AES-GCM additional data on both the data key and the value; a swapped or modified ciphertext fails authentication and the node's assignment is withheld | Mitigated (phase 4) |
| T24 | Host | Info disclosure / DoS | Master key lost, replaced, or world-readable | Created `0600` with `O_EXCL` (never overwritten), loaded only if not group/other accessible; its ID is recorded in the DB and the server refuses to start with a missing or different key; `init` tells the operator to back it up (`armadad backup` includes it) | Mitigated (phase 4) |
| T25 | Admin machine | Info disclosure | Secret values end up in shell history or terminal scrollback | `secret set` takes no value argument; reads from a hidden prompt, stdin, or `--from-file` | Mitigated (phase 4) |
| T26 | Node | Info disclosure | Secret files reach the node's disk or other local users | Written only to a directory verified to be tmpfs/ramfs (otherwise secret files are disabled), root-owned `0700`, removed when the replica goes; bind-mounted read-only; the runtime only mounts regular files at clean absolute paths (`runtime.CheckFileMount`), so they can never mount a runtime socket or a directory | Mitigated (phase 4) |
| T27 | Node | Info disclosure | Secrets leak through container metadata: the spec hash label, or environment variables in the runtime's on-disk container metadata (containerd's) | The spec hash covers only `name@vN` references, never values. Env secrets remain visible to root on the node and are stored by containerd on disk; documented, with `secretFiles` as the alternative | Partially mitigated (phase 4) |
| T28 | Compromised node → server | Info disclosure | An agent obtains secrets of apps it does not run | The server decrypts and sends secrets only inside the assignment for the node that runs the replica (the leader keeps the versions it opened in memory, never on disk, until no replica uses them); the admin secret RPCs require an admin certificate. Node capacity is self-reported: it is bounded and, beyond deciding whether a replica's CPU and memory reservation fits, only breaks ties in scheduling (spread and replica count come first), but a compromised node can still be chosen for new replicas and then receives their secrets. Labels that steer placement and `placement.spreadBy` are set by admins only; `armada.os`/`armada.arch` are agent-reported, so an app spread by them lets a node that misreports its architecture form a value of its own and take that value's share (image platforms rule out architectures the image lacks once known; spread sensitive apps by admin labels) | Partially mitigated (phase 4, 7) |
| T29 | VPC → server | DoS / brute force | Guessing join tokens or flooding the join listener | 256-bit secrets; token buckets per source address (burst 5, then one attempt per 6 s) and overall (burst 30, one per second); at most 4 concurrent streams per connection and a 10 s handshake timeout; failed attempts are logged with the token ID and source address, never the secret | Mitigated (phase 5, hardened in phase 7) |
| T30 | Node | Info disclosure / availability | Renewed key written insecurely, or a crash mid-renewal leaves the node without a usable certificate | The new key and certificate are checked against the CA and the node identity before touching disk, written `0600` as `.new` files, then renamed into place; on start the agent completes or discards a half-finished renewal | Mitigated (phase 5) |
| T31 | Internet / VPC → internal apps | Info disclosure / spoofing | Internal apps reached from outside the cluster, for example through 1:1 NAT or a provider load balancer, or a public name hijacked onto an internal app | The internal frontend binds only to the container bridge gateway, which is not reachable through NAT or load balancers; internal rules exist only in that frontend and public rules only in the public ones; the `.internal` zone is reserved in the spec and revalidated on the agent (`<app>.internal` only); internal apps get no public name, domain, or certificate. A VPC neighbour that routes the bridge subnet via the node could still reach it unless the provider's anti-spoofing or the host firewall stops it | Mitigated (phase 6) |
| T32 | Container / VPC → node DNS | DoS / spoofing | The node resolver abused as an open resolver or reflector, or poisoned | Listens only on the bridge gateway; answers only the bridge subnet and stays silent for everyone else; answers `.internal` authoritatively only for apps the local HAProxy routes; forwards other names to the host's configured resolvers with a 2 s timeout, at most 128 at a time (SERVFAIL beyond that, `.internal` answers unaffected); queries are not cached | Mitigated (phase 6, hardened in phase 7) |
| T33 | Host / backup storage | Info disclosure | A backup archive leaks: it holds the CA key, the master key, and the encrypted secrets together | `armadad backup` writes `0600` and never overwrites; `-o -` refuses a terminal; the command, its help, and the operations guide tell operators to encrypt the archive (e.g. piping into age) before it leaves the host. Armada does not encrypt archives itself | Partially mitigated (phase 7) |
| T34 | Backup storage → server | Tampering / EoP | A modified or malicious archive is restored: path traversal, links, oversized files, swapped keys, or a forged CA | Restore extracts into a fresh temporary directory and accepts only regular files with known names (no directories, no links), with per-file, total, and entry-count limits; every file must match the manifest's SHA-256 and nothing unlisted is accepted; the etcd snapshot must pass its own SHA-256 trailer, restore into a scratch member, and hold state with a schema this binary knows; the master key must match the ID recorded in the state; the CA key must match the CA certificate and the server certificate must chain to it; only then is the directory renamed into place, and never over a non-empty data directory. Checksums detect corruption, not a forger who rewrites the manifest: an archive is trusted as much as wherever it was stored | Mitigated (phase 7) |
| T35 | Admin → server | DoS / tampering | An older binary started against state written by a newer one misreads or corrupts it | The store refuses a keyspace whose schema is newer than the binary knows; operators back up before upgrading and restore that backup to go back | Mitigated (phase 7) |
| T36 | Network / compromised node → server | DoS | Replicas are rescheduled away from healthy nodes (a partition of the control plane, or an attacker cutting its links), or a node flapping on purpose moves replicas around | A node counts as lost only after `--node-lost-timeout` (default 5 min, at least 10 s); if more nodes are lost than ready, nothing is rescheduled; lost replicas are retired only after their replacements serve, so capacity never drops because of rescheduling; returning nodes only remove their stale containers, nothing moves back | Mitigated (phase 7) |
| T37 | Host / VPC → etcd | Info disclosure / tampering / EoP | Another process, another VPC host, or a node or admin certificate reads or rewrites the cluster state in etcd directly, bypassing the API's authorization, validation, and audit log | etcd client and peer listeners require TLS 1.3 client certificates from the cluster CA and accept only the etcd member identity (`AllowedCNs` = `etcd:member`), which is issued only into control plane data directories, so node, admin, and server certificates are refused; the Armada API refuses the member identity in turn; members listen only on the server's private IP (public and wildcard addresses are refused), and peers must connect from an address named in their certificate (the member certificate names the machine's private addresses; the client SAN check stays on); the HTTP gateway and the separate metrics listener are off, and the health and metrics endpoints on the client port need the same client certificate; the member's directory is `0700` and its key `0600`; secret values are stored only encrypted. Root on the control plane host can still read the member key, as it can read the CA key | Mitigated (phase 7) |
| T38 | Admin machine / network → server | Info disclosure / EoP | A server join token is stolen and redeemed to obtain the CA key and the master key, or a node token is used to join as a server | Server tokens are a separate kind (node and server tokens are refused for each other's RPC), single use, 15 minutes by default and at most one hour, stored only as a SHA-256 hash and compared in constant time, read from a prompt, stdin, or a file, never from the command line; the join listener is rate limited and private; the joining machine pins the CA hash, so keys are only sent over a channel to the real cluster; the response's key fields are marked `debug_redact` and never logged; the join is audited (`server.join`). A stolen valid token still yields the cluster's keys: treat it like the CA key | Partially mitigated (phase 7) |
| T39 | Partition / paused process → server | Tampering | Two control plane servers act at once (split brain): an old leader that lost its lease keeps writing, rescheduling, or issuing certificates | Leadership is an etcd election with a 10 s lease; every write of a leader's term is fenced by a compare on the election key's creation revision, so after the term ends writes fail with `ErrNotLeader` and change nothing; etcd itself needs a quorum to commit; a new term starts from fresh in-memory state; certmagic locks are lease-backed etcd mutexes | Mitigated (phase 7) |
| T40 | VPC → etcd peers | Spoofing / DoS | A machine on the private network joins the etcd cluster or disrupts it | Peer traffic is TLS 1.3 with the member identity from the cluster CA; members are added only by the leader as learners after a server token is redeemed; a learner does not count for quorum until the leader promotes it; ports 2379/2380 are documented as open only between servers | Mitigated (phase 7) |
| T41 | Removed server | Info disclosure / EoP | A removed or decommissioned control plane server keeps its copies of the CA key and master key | `armada server delete` removes its etcd member and record, so its member certificate no longer reaches the cluster; the operations guide says to wipe its data directory. CA and master key rotation are not supported in v0.1: a removed server that was compromised means rebuilding the cluster | Accepted |
| T42 | Supply chain → node | Tampering | Tampered containerd, runc, CNI plugin, or tini binaries run as root on every node | Each artifact is pinned by version and SHA-256 in `internal/runtime/embedded/lock.go`; `make runtime-bundle` downloads only over HTTPS and refuses any checksum mismatch; the maintainer verifies upstream signatures (runc, tini) when bumping a version; the pack is embedded in the signed release binary, extracted into a root-owned `0700` directory, and every file is verified against the pack manifest on every start (names are checked, so a pack cannot write outside its directory). Advisories for the bundled components are checked at release time, since `govulncheck` does not see them | Mitigated (phase 7) |
| T43 | Container / host → embedded runtime | EoP / tampering | Another process or a container reaches the embedded containerd, or a container uses it to escape | Armada runs its own containerd instance: socket in a root-owned `0700` directory, no TCP, CRI, debug, or metrics listener; app containers get Armada's defaults (capabilities minus `NET_RAW`/`MKNOD`/`AUDIT_WRITE`, `no-new-privileges`, default seccomp profile, AppArmor where enabled, cgroup v2 memory/CPU/PID limits, own network and cgroup namespaces) and never the runtime socket; published ports are DNAT rules bound to the private IP only (`runtime.CheckContainerSpec`); container IDs that end up in paths (logs, per-container files) are validated. On SELinux hosts every container (HAProxy included) runs as `container_t` with its own MCS categories, its rootfs mounted with the matching context and its bind-mounted files relabelled, so an escaped process cannot read host files or another container's secrets; hosts whose policy lacks the container types run containers unconfined by SELinux and `armadad doctor` warns | Mitigated (phase 7) |
| T44 | Compromised node / admin → scheduler | Spoofing / info disclosure | A node attracts replicas (and their secrets) meant for other machines by claiming labels, or labels are injected into status output and logs | Only admins set labels, with `armada node label` or inside a join token they create (ADR 0014); a node never sends its own labels. The agent reports only its OS, architecture, and container runtime (`armada.os`, `armada.arch`, `armada.runtime`); the server stores them only if they are valid label values and the `armada.` prefix is reserved, so admins and tokens cannot set or remove those keys. Keys and values are whitelisted (lowercase letters, digits, `.`, `-`, `_`, `/` in keys only, 63 characters) on the CLI and again on the server; at most 32 labels per node; label changes are audited. A restricted node runs only apps whose placement names one of its admin labels, which keeps sensitive apps (and their secrets) to chosen machines and other apps off them. A compromised node can still claim another architecture or runtime and receive apps that require it. Image platforms, which restrict placement once known, also come from agents: they are accepted only for a replica the reporting node runs, only as a list of at most 32 `os/arch` entries whose parts are valid label values, and only the first valid list per revision is kept; the control plane does not contact registries to check them. A compromised node can report a wrong list first and keep an app off nodes that could run it A node's first reported image digest pins a revision's image for every node only when the spec names a tag, and only for the same repository; a spec that pins a digest keeps it, and a different digest a node reports is ignored. | Partially mitigated (stage 1) |
| T47 | Admin / node → app container | EoP / info disclosure | `armada app exec` (ADR 0015) is used to run commands with more privileges than the container has, in another node's or an infrastructure container, by a node that hijacks another node's session, or leaks secret values through the audit log, logs, or errors | Only admin certificates may call `AdminService.Exec`, and only node certificates `AgentService.ExecSession`. The server sends each request, with a random ID, only to the node running the replica and accepts its session stream once, from that node only; the agent runs a command only for a replica assigned to it with a running container. The command runs with the container's own process settings (user, capabilities, `no-new-privileges`, seccomp, SELinux label, cgroup, namespaces); the request has no option to change them, and the conformance suite checks the exec process keeps them. The embedded runtime refuses system containers. Commands are checked on the CLI, server, agent, and runtime (at most 64 arguments of 4096 bytes, no NUL bytes); messages carry at most 32 KiB; an agent runs at most 8 sessions and the server ends a session after 30 minutes without traffic. The audit log and logs record the admin, app, replica, command name, and terminal flag, never the arguments. An admin can still read anything the app can, including its secrets: exec adds no authority beyond what an admin certificate already has (it controls images and secrets) | Mitigated (stage 2) |
| T48 | Node → control plane | Tampering / DoS | A node forges resource usage (ADR 0016) for replicas on other nodes to mislead operators (and later autoscaling), or floods the leader with usage reports | Only node certificates may send on the Connect stream, and a usage report is stored under the sending node's identity; a replica's usage counts only from the node it is assigned to, checked when the sample is read. Values are bounded to plausible ranges, a report with more than 1024 replicas is dropped, and the leader keeps only the latest sample per node, in memory, for 35 seconds and until the node disconnects, so reports cost no store writes. A node can still misreport its own replicas' usage, as it can their state | Mitigated (stage 2) |
| T49 | Private network / stolen credential → control plane | Info disclosure / EoP | The metrics endpoint (ADR 0017) exposes app, replica, node, and revision names to anyone on the private network, or a metrics certificate is used for more than scraping | The endpoint is off by default, binds only to a private address, and only the leader serves it; it requires TLS 1.3 and a client certificate from the cluster CA, and serves only `metrics:` identities and principals with cluster-admin (node and server certificates get 403).
